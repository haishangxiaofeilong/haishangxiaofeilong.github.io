一次完整推理，模型背后要走完 5 道工序

2026-09-07 3113 字— 次阅读

你问大模型一句话，它回你一段字。

看起来是一次对话，背后是一条流水线。

我在《大模型推理的两阶段：一次 Prefill，加上多次 Decode》里讲过，Prefill 和 Decode 这两步是怎么接力的。

那两步只是这条线中间的两道工序。

上篇末尾点名要展开的那几样，tokenize、scheduling、KV cache 的分配、embedding、detokenization，外加加载模型时到底加载了什么，这篇挨个拆。

往前看，你的问题得先被切成 token，还得有人给它排队、安排计算和 KV cache 资源。

往后看，模型吐出来的是一串编号，还得再翻译回文字。

你的问题，得先被切成 token

token 是什么意思，我在《大模型推理时，到底在干一件什么事？》里讲过，这里只看它怎么被切出来。

第一道工序叫 Tokenize（分词）。

拿 "What is LLM inference?" 这句提问来说，经过某个 tokenizer 之后，可能会被切成下面这几块。

What、is、LLM、infer、ence、?

inference 这个完整单词被切成了 infer 和 ence 两块，所以 token 不一定等于一个单词。

中文也一样，一个词切成好几个 token 很常见。

具体怎么切，取决于这个模型配套的 tokenizer，不同模型、不同版本切出来的结果都可能不一样。

干这活的是 tokenizer（分词器）。

它通常作为模型配套的独立组件提供，模型部署时需要一起加载。

而且分词器是跟着模型走的。

DeepSeek 用 DeepSeek 的 tokenizer，Qwen 用 Qwen 的。

拿 DeepSeek 切出来的 token 去喂 Qwen，Qwen 根本读不懂那些编号。

调度：活还没开始，先把位置安排好

分完词，服务端的推理引擎还要做一件事，叫 Scheduling（调度）。

调度发生在真正计算之前，而且不止做一次。

每一轮推理，调度器都可能重新决定哪些请求先跑、这一轮分给它们多少资源。

开头这一轮，主要可以理解成两件事。

一件是安排 KV cache 的存储空间。

大模型里有一层层的注意力层，算注意力需要 Q、K、V 这三样东西，其中 K 和 V 后面还要反复用，得存进 KV cache。

在采用分块 KV cache 管理的推理框架里，调度器会根据请求的 token 数量和当前显存情况，为请求分配相应的 KV cache 空间。

Prefill 算出 K 和 V 后，再把它们写进去。

另一件是安排队列：

哪些请求这一轮先跑，以及这一轮各自处理多少 token。

说人话就是，客人还没进门，先把桌子怎么摆、谁先坐安排好。

中间那两步：Prefill 和 Decode

接下来才轮到它们。

这里只说它们在整条线上处在什么位置。

Prefill 干的活，是把刚才切好的那几个 token 一次性送进模型，一次完成这段输入的前向计算，顺手把每层算出的 K、V 写进刚安排好的 KV cache，然后根据最后位置的 logits 选出第一个生成 token。

之后 Decode 接手，通常一轮生成一个 token，直到满足停止条件。

前面那些工序，全都是在给这两步铺路。

还有一层容易被跳过：embedding

token 进了模型，第一站是 embedding 层。

这一层算在模型内部，不占流水线上的独立工序。

它的作用很单纯，把 token ID 映射成向量。

后面的注意力层、前馈层，处理的都是这些向量。

通常，这一层属于模型本体的一部分。

顺带说一个容易混的点：

RAG 里也总在说 embedding，很多人因此以为两者是同一件事。

它们要解决的问题不一样。

模型里这一层负责 token ID 到向量的映射，后面几十层都在这个向量上做计算。

RAG 那边要把一整段文本压成一个能做语义检索的向量，这活通常由专门的 embedding 模型来干。

模型自己跑推理的时候，它自带的这一层一直在工作。

模型吐出来的是一串编号

Decode 每轮会根据模型输出的 logits，选出一个 token ID。

要变成你看到的字，还得再走一步 Detokenization（反分词）：

把生成的 token ID 按 tokenizer 的规则还原成文本。

流式输出时，新生成的 token 会被持续增量解码，逐步变成你看到的文字。

所以完整链条是这样走的：

你输入的文字 → token ID → 模型跑前向计算（Prefill 和 Decode）→ 新的 token ID → 你看到的回复。

这一进一出，都由 tokenizer 相关组件负责。

所以推理时，至少离不开哪两样

平时说"加载一个 7B 模型"，如果只看和文本推理直接相关的核心部分，可以先抓住两样：

组件 规模 干什么用
tokenizer（分词器） 通常远小于模型权重 开头把文字切成 token，结尾把 token ID 转回文字
model（模型本体） 7B、8B 这样的大块头 跑 Prefill 和 Decode，完成主要的神经网络计算

除此之外，模型目录里通常还有配置文件、词表相关的文件等辅助文件。

tokenizer 相比模型权重小很多，但同样少不了：

模型负责算，tokenizer 负责在文字和 token ID 之间来回转换。

串起来看

把整条线拉直了就是：

Tokenize → Scheduling（安排 KV cache 空间、排队）→ Prefill → Decode → Detokenization。

Embedding 没单独列进去，因为它本身就是模型计算的一部分。

Prefill 和 Decode 是站在台上干活的两位，但把它们托起来的，是前面分词和调度、后面反分词这一整套工序。

这条线走完，还剩一个更现实的问题。

同样是一次推理，为什么有的模型让你干等着第一个字迟迟不出来，有的却几乎立刻开口？

一个卡在 Prefill，一个卡在 Decode——慢到底慢在哪，下一篇我们把这两个时间拆开看。
