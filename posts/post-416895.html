为什么 synchronized 管不了集群？Redis 分布式锁到底解决了什么问题？

2026-08-05 2304 字— 次阅读

面试官最爱顺藤摸瓜的一连串

面试官问你 Redis 用在项目哪些地方，你若答"分布式锁"，他八成追一句：那它怎么实现的？

这种题有个坑：

别急着背原理，得先把使用背景讲清楚——什么业务、什么场景，才逼得你上分布式锁。

说白了，凡是多个节点一起抢同一份资源、本地手段兜不住的时候，分布式锁就得出场。

它常出没在这些场景里：

场景 说明
集群定时任务 多节点部署时，避免同一任务被重复执行
抢单 / 抢券 多个请求同时争抢一份有限资源
秒杀 高并发库存竞争场景下，保证扣减逻辑的一致性
接口幂等性 防止重复提交造成重复处理

从一个抢券逻辑说起

先看一段简化后的抢券代码，把流程拆开。

// 简化示例：实际生产环境不会直接读改写库存
public void grabCoupon() {
    // 查询库存
    int stock = couponService.getStock();

    // 没库存，抢券失败
    if (stock <= 0) {
        throw new RuntimeException("优惠券已抢完");
    }

    // 扣减库存
    stock--;

    // 更新库存
    couponService.updateStock(stock);
}

第一步，读优惠券库存。

数量有限，上线前就配好。

拿到数量后，先判断是不是抢光了。

归零就抛"优惠券已抢完"的异常，请求结束。

还有余量，就执行减一，证明这张券被你拿走，最后把新库存写回去。

流程长这样：

单线程执行时，这段逻辑没有问题。

并发一来，这套逻辑就漏了

单线程执行时，这段逻辑没有问题；但两个线程同时进入，漏洞就出现了。

正常情况：

线程一查券、判断够、扣减；

线程二走一样流程，相安无事。

但线程是交替跑的。

设想库存只剩 1 张时——

线程一刚查完库存，还没判断，线程二也查了一次。

两个都读到 1，都觉得"还有货"。

线程一扣减成功，库存变成 0；

线程二拿着自己读到的旧库存 1，也认为还有库存，继续执行扣减。

最终导致两个请求都成功，但实际库存只有一张。

超卖了。

这能忍？

本地锁救得了单体，救不了集群

有人立马想到加锁。

给这段代码套一层 synchronized 行不行？

单体项目里，还真行。

线程一拿到互斥锁，查券扣减一气呵成；

线程二进入阻塞等待状态，直到线程一释放锁。

等线程一释放，线程二才进场。

这方案成立的前提是：

服务只有一台，跑在单个 JVM 上。

可现实为了扛并发，同一份代码往往部署成集群。

比如 8080、8081、8082 三台服务，前面挂 Nginx 做反向代理和负载均衡。

这时候 synchronized 就露怯了。

左边 8080 的线程拿本地锁查了券，右边 8081 的线程也拿本地锁查了券——两边都能读到数据。

原因很直白：

它是本地锁，锁挂在 JVM 上。

每台服务各有一个 JVM，只管得住自己进程内的线程互斥，跨 JVM 根本管不了。

Redis 分布式锁正式登场

本地锁管不了跨进程，那就把锁挪到外面——用 Redis 当这把外部锁。

流程变成：

线程一先去 Redis 尝试加锁，成功后 Redis 保存这把锁对应的 key 和持有者信息。

加锁失败后，需要等待锁释放，再重新尝试获取。

等左边持锁线程跑完业务、释放了锁，Redis 记录清掉，右边线程一才能拿到锁，再去查券、判断库存。

在正常情况下，只要有人持锁，其他线程无法同时获取同一把锁，互斥效果就实现了。

实际实现时，一般使用 Redis 的 SET key value NX EX 命令，一次完成加锁和过期时间设置，避免锁一直占用。

结论很明确：

在秒杀、抢购这类库存竞争场景中，如果业务逻辑比较复杂，需要保证多个节点之间的互斥执行，分布式锁就是一种常见方案。
