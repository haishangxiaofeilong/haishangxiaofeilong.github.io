MySQL 回表：为什么走了索引还要再查一次 B+ 树？

2026-08-17 2079 字— 次阅读

MySQL 面试里有一个绕不开的问题：

为什么走了索引，还需要回表？

官方文档并没有给它正式定义，但它连着聚簇索引、非聚簇索引、覆盖索引一整条线，查询优化时经常撞上。

一句话说清楚：

回表就是用二级索引查数据时，叶子节点只给了一个主键值，MySQL 还得再拿这个主键去聚簇索引里把整行数据"捞"回来的那一步。

聚簇索引和非聚簇索引，叶子节点不一样

InnoDB 的索引分两种。

聚簇索引的叶子节点存的是整行记录，也就是按主键组织好的完整数据。

除了聚簇索引之外，其他索引在 InnoDB 中都属于二级索引，也叫非聚簇索引。

它们的叶子节点不存整行，只存两样东西：

索引字段的值，以及对应的主键值。

非聚簇索引没有保存完整数据

非聚簇索引的叶子节点不存整行，只放索引字段的值和对应的主键。

查数据的时候，它手里只有主键这一个"门牌号"，拿不到 age、gender、address 这些字段。

举个容易理解的例子。

非聚簇索引像餐厅的菜单，上面只有菜名和对应的出餐口编号。

出餐口编号就是主键。

你光看菜单拿不到菜，得拿编号去后厨窗口，才能把整道菜端出来。

后厨里按编号排好的整道菜，就是聚簇索引里的整行数据。

从菜单到后厨窗口多走的那一步，就是回表。

回表到底是怎么发生的

拿一张 user 表举例：

CREATE TABLE user (
  id INT PRIMARY KEY,
  name VARCHAR(50),
  age INT,
  gender VARCHAR(10),
  address VARCHAR(200),
  INDEX idx_name (name)
);

id 是主键，所以主键索引就是聚簇索引。

name 是普通索引，属于非聚簇索引。

执行下面这条 SQL：

SELECT * FROM user WHERE name = '张三';

MySQL 会先走 idx_name 这棵 B+ 树，找到 name = '张三' 的那条记录，从叶子节点里取出对应的 id。

注意，这时候它手里只有 id，没有 age、gender、address 这些字段。

要拿完整行，必须再拿着 id 去聚簇索引走一趟，把整行捞出来。

这一步，就是回表。

回表的代价

回表多走了一趟聚簇索引，开销直接上来了。

第一个影响是增加 IO 访问次数。

如果目标数据页不在 Buffer Pool，除了访问二级索引外，还需要额外访问聚簇索引对应的数据页。

第二个影响是数据库负载。

查询返回大量数据时，大量回表访问会增加聚簇索引的访问次数，提升 CPU 和 IO 压力。

实际场景中，能避免回表就尽量避免。

怎么避开回表

有三种常见的思路。

第一种，用覆盖索引。

覆盖索引指的是要查的字段刚好都在非聚簇索引里，MySQL 不需要再回聚簇索引拿数据。

上面那张 user 表，name 是普通索引，它的叶子节点里本来就存了 id 和 name（因为 InnoDB 的二级索引叶子节点默认保存主键值），所以这条语句不回表：

SELECT id, name FROM user WHERE name = '张三';

id 和 name 都在 idx_name 这个索引里，索引自己就能把结果给全。

第二种，尽量直接走主键。

主键索引的叶子节点就是整行数据，查主键天然不回表，效率最高。

第三种，少查字段，别用 SELECT *。

反过来想就清楚了：

前面那条 SELECT * FROM user WHERE name = '张三'，因为要的是整行，索引给不全，才不得不回表。

把要查的列收敛到索引覆盖范围内，回表这一步就没了。

最后串一下

回表就是 InnoDB 用二级索引查到主键后，还得再拿主键去聚簇索引把整行取回来的过程。

非聚簇索引叶子节点保存索引字段和主键，不保存完整数据行，决定了这一步省不掉；

想绕开它，就用覆盖索引、优先走主键、少查字段。
