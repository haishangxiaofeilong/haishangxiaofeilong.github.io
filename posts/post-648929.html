大模型推理的两个速度指标：TTFT 和 ITL 分别卡在哪一段

2026-09-08 2176 字— 次阅读

你问大模型一句话，它回你一段字。

字是一个一个蹦出来的，但你大概率有过这种体验：

第一个字要等好久，等它一冒头，后面的字就刷刷往外跑。

这两段等待，其实对应两个完全不同的性能指标。

我在《大模型推理的两阶段：一次 Prefill，加上多次 Decode》里讲过，模型一次生成可拆成 Prefill 和 Decode；

我在《一次完整推理，模型背后要走完 5 道工序》里也带过，这两步站在流水线中间。

这篇就先用两个指标，把最直观的"慢"拆开看看：

TTFT 和 ITL。

一个主要看第一个 token 要等多久，一个主要看后面的 token 生成得有多快。

TTFT：你等第一个字，到底在等什么

TTFT（Time To First Token，首个 token 的等待时间），说白了就是从请求发出去，到模型返回第一个 token，中间等了多久。

它的核心计算环节是 Prefill。

Prefill 要干的事，是把你整段提示词一次性送进模型，跑一遍前向计算。

提示词越长，通常要处理的 token 越多，Prefill 的计算量也越大；

这一步完成后，模型会根据最后位置的输出 logits，用贪心或采样等解码策略得到第一个 token。

不过，实际测出来的 TTFT 不只包含 Prefill 本身，还可能包含请求排队、调度等带来的等待。

所以想让第一个 token 早点出来，主要有两条路。

一条是减少生成前的等待，别让请求因为 GPU 忙、调度或者资源不足在那里排队等。

另一条是把 Prefill 本身跑快，比如优化算子、提高硬件利用率。

核心就一句：

想压 TTFT，主要盯着 Prefill 和生成前的等待折腾。

ITL：后面的字，为什么快不起来

第一个 token 出来之后，模型进入 Decode，一个一个生成后面的 token。

每两个相邻输出 token 之间的时间间隔，叫 ITL（Inter-Token Latency，token 间延迟）。

这段时间主要反映 Decode 阶段每一步生成 token 的耗时。

对于单条请求，Decode 每一轮通常只生成一个新 token。

这个新 token 在注意力计算时需要利用前面的上下文，但历史 token 的 Key 和 Value 可以通过 KV cache 直接复用，不需要每轮重新计算。

所以，Decode 慢不慢，除了当前这轮计算本身，还和需要读取、参与注意力计算的历史 KV 有关；

同时，实际观测到的 ITL 还可能受到调度、Detokenization 和流式输出等环节影响。

想让后面的字出得更快，就得去 Decode 这段找原因：

这一轮到底算了什么、需要读多少历史 KV，又被什么资源卡着。

找准了，才有办法压下去。

核心也一句：

想压 ITL，主要盯着 Decode 和它背后的资源瓶颈。

一张表看清两个指标

指标 量的是什么 核心计算环节 优化该动哪
TTFT 从请求到第一个 token 的等待时间 Prefill + 前置等待 减少排队、提高 Prefill 计算效率
ITL 相邻输出 token 之间的时间间隔 Decode 为主 优化 Decode、缓解资源瓶颈

很多人以为"推理慢"是个整体问题。

其实它至少可以拆成两半：

头一个 token 的等待，和后面每个 token 之间的间隔，是两类不同的问题。

所以优化时别瞎忙：

第一个 token 慢，先看 TTFT；

后面的 token 间隔大，再去看 ITL。

力气别使错地方。

顺带说一个容易混的点

Decode 每生成一个 token ID，后面通常还要经过 Detokenization，把这个 token ID 转成人能看到的文本。

所以你看到的"字一个一个蹦"，背后并不只有模型 Decode，还涉及 Detokenization 和流式输出。

它们是不同的处理环节，最终共同影响用户看到文字的速度。

把 TTFT 和 ITL 分开看，最大的好处是优化时方向清楚。

但 Decode 为什么能一轮一轮生成 token，而历史 token 的 Key 和 Value 又为什么不用每轮重新计算？

背后站着一个关键东西：

KV cache。
