明明建了索引，MySQL 却不用？这 8 种情况它悄悄放弃了

2026-08-24 3991 字— 次阅读

索引失效这件事，面试八股里几乎人手能背几条：

like 左边加 %、对字段套函数、隐式转换……

这些都没错。

但很少有人被追问一句，“它们为什么会让索引失效？”，还能答得让面试官满意。

把原因拆开看，其实只有两条线。

一条是结构性的——你写出来的 SQL 让查询条件无法直接利用 B+ 树已有的有序结构，MySQL 无法直接利用这棵普通索引树进行有效定位，通常需要选择其他访问方式；

另一条是成本性的——B+树还在，但优化器算了一笔账，觉得走索引比全表扫描还慢，于是最终没有选择走索引。

结构性失效和成本性失效这两类搞混了，你背再多场景都是死记硬背。

下面把每条场景都归到"结构性"和"成本性"这两条线上，你看完就知道哪些能避免、哪些由不得你。

先说结论

开发者常说的"索引失效"，通常是指：

表上明明存在索引，但某条 SQL 执行时，优化器没有选择通过这个索引来访问数据。

原因分两类（这里为了方便理解，是我自己建立的分类，不是 MySQL 官方术语）：

  • 结构性失效：查询条件无法直接利用普通索引已有的有序结构（对索引列套函数/表达式、隐式转换、左模糊、没有形成有效的左前缀），普通索引无法直接形成有效的定位条件，通常无法通过这个索引做高效的范围/等值查找，优化器可能选择全表扫描、全索引扫描等其他访问方式。
  • 成本性失效：索引本身能够使用，但优化器根据成本估算，认为某种索引访问路径不如其他方案划算（低基数字段、小表、大结果集、统计信息不准，以及 OR / Index Merge 等复杂访问路径选择），于是最终没有选择这个索引访问方案。

后面每一条场景，都是在为这两条线找具体的落点。

对索引字段套了函数或表达式

你写了 WHERE DATE(create_time) = '2025-11-11'，或者 WHERE YEAR(create_time) = 2025——这些都是对索引字段做了加工。

普通 create_time 索引建立的是原始列值的有序结构：2025-11-11 01:00:00 按原始值排好序，所以能二分定位。

但查询条件要求按 DATE(create_time) 这个表达式的结果来判断。

普通的 create_time 索引并没有直接建立在这个表达式结果上，因此无法根据该表达式的结果进行有效定位，这个条件也就难以通过这棵普通索引完成范围查找，优化器通常只能选择其他访问方式，例如扫描数据后逐行计算 DATE()。

说白了，索引是按"原值"建的，你却拿"加工后的值"去查，树帮不上忙。

这里的关键是"无法直接利用普通索引的有序结构"，而不是 SQL 真的把 B+ 树搞坏了。

而且 MySQL 8.0.13 以后支持函数索引，可以直接对表达式建索引（INDEX ((DATE(create_time)))），那就不存在这个问题了。

所以更好的写法是把函数从列上挪走，改成对原始列的范围判断：

WHERE create_time >= '2025-11-11 00:00:00'
  AND create_time <  '2025-11-12 00:00:00'

记住一条：

不要把函数套在索引列上，尽量把条件改写成对原始列的范围判断。

隐式类型转换

字段是 VARCHAR，你却拿数字去查：

WHERE phone = 15810111111。

MySQL 发现两边类型不一致，会按照类型转换规则进行隐式转换。

问题在于，如果转换方式导致索引列无法保持原本的索引比较形式，就可能无法利用普通索引进行高效定位。

这跟上一节套函数是同一个后果：

查询条件无法直接利用普通索引已有的有序结构。

正确的写法是 WHERE phone = '15810111111'，把查询值也变成字符串，两边类型一致，可以避免不必要的类型转换，更有利于直接利用索引进行查找。

like 左边是 %

WHERE name LIKE '%明' 或者 WHERE name LIKE '%小%'——% 打头，意味着你要找的是"结尾或中间包含某串"的数据。

B+树的有序是"从左到右"的。

索引能帮你快速定位"以某串开头"的数据，因为开头定了，范围就锁定了。

但 % 在最左边，意味着无法根据字符串开头形成有效的索引范围，因此普通 B+ 树索引无法帮助我们快速定位匹配范围，通常只能扫描大量索引记录或数据后再进行匹配。

WHERE name LIKE '小%' 这种"右边是 %"的写法不会破坏字符串开头的有序性，可以形成有效的索引范围，但最终是否选择这个索引，仍然要看优化器的成本判断。

违反组合索引的最左匹配

建了组合索引 (a, b, c)，就得从左往右用。

你写 WHERE b = 1 AND c = 2，跳过了最左边的 a。

这种情况下，通常无法按照普通的左前缀方式去利用后面的索引列——就像查电话簿，它按"姓→名→号"三级排序，你只拿"名"去查，前面姓是空的，顺序就乱了，只能翻遍整本。

不过现代 MySQL 还有 Skip Scan 等优化，具体能不能、要怎样用到索引，还要看版本、数据分布和优化器选择，不能说"一定完全用不上"。

WHERE a = 1 AND c = 2 这种跳过中间 b 的，在普通的联合索引范围访问中，a 能形成有效的左前缀定位，而 c 虽然出现在条件里，却无法像 a、b 那样直接形成连续的索引定位条件，通常需要作为 a 命中之后的后续过滤条件来处理，所以一般最多用到 a 那一段。

or 不等于索引失效，但会增加优化器的选择难度

WHERE indexed_col = 1 OR non_indexed_col = 2——or 的一边有索引，另一边没建索引。

这不意味着索引一定失效。

对于两边都具备可索引条件的情况，MySQL 甚至可能使用 Index Merge，分别扫描多个索引再合并结果；

如果其中一边没有可用索引，优化器仍可能选择利用另一边索引后再做过滤，但也可能认为整体成本过高而直接全表扫描。

最终能否用索引、用哪种，取决于具体数据和成本估算。

所以 OR 本身不是"索引失效"的硬场景，它更适合归到"优化器访问路径选择"这一类：

能不能用索引、用哪种，取决于成本，而不是"有一边没索引就必定全表"。

低基数字段上建索引

gender 只有男、女两个值，status 只有 0、1、2 几个值——这种字段通常选择性较低，单独建立索引的收益可能有限。

索引的价值在于"快速缩小范围"。

一个值占了半张表，走索引先查到一堆行、再回表，还不如直接从头扫一遍。

优化器算完这笔账，可能会放弃索引，选择全表扫描。

表太小，或者结果集太大

两种相反的极端，结局一样——优化器可能放弃索引：

  • 表太小：一张表只有几条、十几条记录，全表扫描本身比"走索引再回表"还快，优化器直接选全表。
  • 结果集太大：当查询需要返回表中很大一部分数据时，走索引意味着大量索引扫描加回表，回表的随机 IO 成本可能比顺序扫全表还高，优化器也可能放弃索引、改走全表扫描。没有固定的比例阈值，最终看成本模型怎么算。

这条是纯成本判断，你 SQL 写得再标准也没用，是数据分布本身决定的。

统计信息过期，误导了优化器

优化器靠表的统计信息来估算"走索引贵不贵"。

你做了大量增删改，但统计信息没更新，如果统计信息不能准确反映当前数据分布，优化器对选择性、扫描行数等的估算就可能出现偏差，从而选出并不理想的执行计划，放弃了一个本该有用的索引。

解决办法是 ANALYZE TABLE 表名，它可以更新相关统计信息，让优化器基于更接近当前数据分布的信息重新估算执行计划。

把上面这些场景梳理一下，可以归到两条主线上：

第一类：

条件本身难以利用普通索引——对索引列做函数/表达式、不合适的隐式类型转换、LIKE '%xxx'、联合索引没有形成有效的左前缀。

这类属于能靠改写法避免的。

第二类：索引能用，但优化器认为不划算，或访问路径更复杂——低基数字段、表太小、需要返回大量数据、统计信息不准，以及 OR / Index Merge 这类复杂条件下的访问路径选择。

这类更多由数据分布和成本模型决定，改 SQL 也未必救得回来。

面试时先抛"结构性 + 成本性"这条主线（本文自己的分类框架），再往下举例，比直接背八条清单清楚得多。

真碰上优化器选择了不理想的索引时，FORCE INDEX 可以告诉优化器优先使用指定索引，但是否应该这么做仍要结合 EXPLAIN 和实际执行效果判断；

ANALYZE TABLE 可以更新统计信息，帮助优化器重新估算执行计划——这两个是常用的干预手段，但也不是万能兜底。
