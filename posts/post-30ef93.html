SFT 数据到底喂到什么火候，才轮得到 RL？

2026-09-01 3800 字— 次阅读

核心结论

在典型的 RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习） / 在线 RL（Reinforcement Learning，强化学习）对齐流程里，通常要先用 SFT （Supervised Fine-Tuning，监督微调）把模型练到"会正经答题"，再考虑 RL 上场。

更关键的判断标准不是 SFT 跑了多少条数据，而是：

同一个 prompt 采出来的多个回答之间，是否已经存在稳定、可区分、可优化的质量差异。

哪怕提前上 RL，效果也可能很差。

关键不在于 reward 是正还是负，RL 并不要求必须采到"正奖励样本"。

真正重要的是：

模型对同一道题采出的多个回答之间，得存在能被 reward 区分的质量差异。

如果 SFT 还没把模型拉到能正经答题的区间，采出来的回答几乎都在答非所问、候选之间缺乏稳定可靠的质量差异，那 reward 信号也难提供有效的优化方向。

为什么不能直接上 RLHF

预训练模型的核心目标是 next-token prediction（预测下一个 token），而不是专门优化"理解用户指令并完成任务"。

你给它一句"请用三句话解释量子纠缠，并给一个生活类比"，它大概率顺着已有文本往下续写，而不是真的按你的指令去组织答案。

那直接上 RLHF 不就行了？

这里有个致命问题。

RL 要让模型从反馈里学，前提是模型采出来的多个回答之间，存在能被 reward 区分的质量差异。

你拿还没对齐的 GPT-3 去采 100 个回答，可能没有一个在真正答题，全是在做文本补全。

如果模型的采样分布过于差、候选之间缺乏稳定可靠的质量差异，reward 信号的有效性就会很弱，RL 很难学到真正有用的策略改进。

说白了，RL 不一定需要"高分种子"，但需要一个已经能产生不同质量候选答案的策略分布。

SFT 就是先把苗子喂起来的那一步。

类比 AlphaGo，可以把它理解成类似的思路：

先通过监督学习获得基本棋力，再通过自我对弈继续优化策略。

两者训练流程并不一一对应，但"先打基础、再自我提升"的逻辑是相通的。

SFT 这一阶段的任务很明确：

让模型学会基本的对话格式和指令跟随。

SFT 要练到什么程度

光说"练到位"太虚，我一般从四个角度判断。

先看模型能力靠不靠谱

SFT 到位的标志是模型有了稳定的指令跟随能力，大方向不跑偏。

你问它问题，它老老实实回答，不再做文本补全，也不再答非所问。

用技术语言说，就是模型已经形成了稳定的指令跟随行为，输出不再是文本续写。

再看数据规模够不够

数据量没有一个统一的"够了"标准，它受模型规模、基础模型能力、数据质量和任务复杂度影响。

拿公开资料里的 DeepSeek LLM 举例，它的对齐阶段收集了约 150 万条中英文 instruction data，其中约 120 万条偏 helpfulness，30 万条偏 safety。

7B 模型训练了 4 个 epoch，而 67B 模型只训练 2 个 epoch，因为更大的模型更容易过拟合。

值得注意的是，DeepSeek LLM 在 SFT 之后采用的是DPO（Direct Preference Optimization，直接偏好优化），而不是PPO（Proximal Policy Optimization，近端策略优化）这类在线 RL；

而 DeepSeek-V2 也采用了 SFT → RL 的路线，并在 SFT 之后使用 GRPO（Group Relative Policy Optimization，组相对策略优化）做进一步对齐。

这个例子更直接地说明：

SFT 和 RL 之间并不存在一条固定的数据量分界线。

两者放在一起看更说明一件事：

决定下一阶段的不是"150 万"这个数字，而是具体的模型能力、训练目标和能拿到的反馈信号。

reward 采样有没有足够的"可优化空间"（这条最关键）

拿 SFT 后的模型，对着同一个 prompt 采多个回答，看它们之间是否已经出现稳定的质量差异。

比如有的回答明显答错，有的基本正确但不完整，有的正确且表达清晰。这说明模型已经进入了"会做，但做得不稳定"的阶段。

这种时候，继续单纯依赖 SFT 的成本开始上升：

你得继续人工写一条条"标准答案"告诉模型怎么做。

而偏好优化更擅长解决另一类问题：

多个答案都不是完全不能用，但明显有的比另一些更好。

这时候，无论是 reward model 还是规则 verifier，都能提供排序信号，让 RL 把策略逐渐推向更高质量的输出。

反过来，如果模型对大多数 prompt 都还不会做，采样出来的回答几乎没有可用候选，那继续补 SFT 或训练数据，通常比直接上 RL 更划算。

判断切不切 RL，更应该看这条：

模型采样结果之间，是否已经存在稳定、可区分、可优化的质量差异。

最后看标注成本扛不扛得住

SFT 需要人工标注完整的 prompt-response 对，成本不低。

想继续用 SFT 提质量，就得不停地标新数据，这个循环很痛苦。

在典型的 RLHF 流程里，模型先生成多个候选回答，再靠人工或其他反馈机制给出偏好信号；

这些偏好数据用来训练 reward model，在线 RL 再利用 reward model 给出的奖励去优化策略。

在很多复杂生成任务里，这比从零编写完整标准答案更容易规模化，但偏好数据和 reward model 本身依然需要投入，谈不上"效率一下子就上来"。

第二阶段对齐：从"会答"到"答得更好"

SFT 之后，模型已经具备基本的指令跟随能力。

接下来要解决的就不再只是"会不会答"，而是"多个都能答的答案里，哪个更好"。

这时就可以引入偏好优化或 RL。

维度 SFT 偏好优化 / RL
对齐目标 学会对话格式、指令跟随 在多个可行答案中进一步优化质量
给模型什么信号 demonstration preference / reward
能表达什么 "这样回答" "这个比那个更好"
负反馈利用 标准 SFT 主要依赖正例 可利用 chosen / rejected 偏好对
典型方法 SFT DPO、PPO、GRPO 等

SFT 用单一的 demonstration 告诉模型"这样回答"，但说不清"哪个回答更好"。

在 RLHF 里，reward model 会给不同回答提供奖励信号，再由在线 RL 优化策略；

而 DPO 这类直接偏好优化方法则可以绕过显式 reward model，直接利用 chosen / rejected 偏好数据优化模型。

相比只模仿一条 demonstration，偏好建模更自然地表达"这个比那个差"。

你可以标出哪些回答不好、不安全，用 pairwise loss 这种 learning to rank 的方式建模，让 reward model 学习回答之间的相对偏好。

SFT 也能通过 rejected 数据、DPO 等偏好方法用上负反馈，只是"相对优劣"本就是偏好优化这一路的强项。

PPO 这类典型在线 RL 方法的优势，是可以直接针对模型当前采样出来的输出做优化，并通常会加入相对于参考模型的 KL（Kullback-Leibler，KL 散度） 惩罚，控制当前策略不要过度偏离参考模型（通常就是 SFT 模型）。

一个实战判断框架

要不要切 RL，我一般看三个条件同时满足：

模型对同一 prompt 采样的回答之间，已经存在稳定、可区分的质量差异，而不是清一色都很差。

你的任务存在可以可靠评估的优化目标，例如人工偏好、规则 verifier、结果奖励等。

值不值得上 RL，得看它的收益能不能盖过额外的算力和工程成本。

反过来，如果任务对输出格式要求特别严，或者模型规模还小、本身不够稳，那继续打磨 SFT 数据质量往往是更稳妥的选择。

这里没有绝对标准，得看具体场景权衡。
