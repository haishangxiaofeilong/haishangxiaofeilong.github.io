面试官：你说懂 AOP，那 Spring 到底是怎么把方法“插进去”的？

2026-07-21 5366 字— 次阅读

在之前的文章Spring Boot 核心就这 3 件事中有读者留言，问我能不能讲讲Spring AOP，今天就来聊聊Spring AOP。

AOP 要解决什么问题？

很多人把 AOP 想得特别复杂，其实说白了，它要解决的问题就一个：

代码写完了，突然发现有一堆公共逻辑要加进去，但不想一个一个方法去改。

打个比方：

你的项目已经上线了，里面有一百多个方法。

这时候产品经理跑过来说，所有接口都要加权限校验。

你怎么办？

打开那一百个方法，每个方法第一行都手写 checkPermission()？

这要是以后还要加日志、加参数校验、加限流呢？每个方法都加四遍？

那不直接就裂开了。

所以 AOP 就出来了。

AOP 叫面向切面编程（Aspect-Oriented Programming），它的核心思路是：

把那些跟业务无关的公共逻辑抽出来统一处理，业务代码本身一行都不用动。

说人话就是——

你在公司大楼门口装了一个安检仪。

不管你是去财务部还是技术部，所有人都要先过安检。

财务部不需要自己雇保安，技术部也不需要。

业务代码只管业务，公共逻辑交给 AOP。

那 AOP 具体怎么做到的呢？

拆开来看，先搞清楚它里面的核心概念。

AOP 的核心概念

切面（Aspect）

切面是 AOP 的核心载体。

什么叫切面？

就是把多个类中重复出现的通用行为，封装成一个可重用的模块。

比如你要做日志记录，那你就写一个类，把日志相关的代码全部放进去。

这个类，就叫"日志切面"。

在 Spring 里，用 @Aspect 注解来标识一个切面类：

@Aspect
@Component
public class LogAspect {
    // 日志逻辑写在这里
}

一个项目可以有若干个切面，就像一栋楼里有多个安检口：入口安检、电梯安检、VIP 通道安检，各管各的。

通知（Advice）

光有切面还不够。

你还得告诉 Spring：

这个切面里的逻辑，在方法执行的哪个阶段执行？

是在方法调用之前？调用之后？正常返回之后？还是抛出异常的时候？

Spring AOP 中常用的通知类型主要有五种：

前置通知（@Before）：

目标方法执行之前触发。就好比进门先登记。

后置通知（@After）：

目标方法执行之后触发，不管成功失败都要执行。

就好比走的时候打个招呼。

它类似于 finally 块，无论目标方法正常返回还是抛异常都会执行。

返回通知（@AfterReturning）：

目标方法正常返回后才触发。就好比办完事盖个章。

异常通知（@AfterThrowing）：

目标方法抛出异常时才触发。就好比出事有人接手。

环绕通知（@Around）：

包裹整个方法调用过程，是最强的一种通知。

通知类型 执行时机 一句话理解
@Before 前置通知 方法执行前 进门先登记
@After 后置通知 方法执行后 走时打招呼
@AfterReturning 返回通知 正常返回后 办完盖章
@AfterThrowing 异常通知 方法抛异常时 出事接手
@Around 环绕通知 包裹整个调用 全程陪同

那这五种通知怎么选？

看需求。

记个日志，前置通知就够了。

但如果你要做缓存优化，命中缓存就直接返回、不调用目标方法，那只能用环绕通知，因为只有它能决定目标方法执不执行。

说白了，前四种通知都是在方法的某个时间点"插一脚"，而环绕通知是站在方法门口，想不想让你进去，它说了算。

切入点（Pointcut）

通知解决了"什么时候执行"，切入点解决的是"对哪些方法执行"。

举个例子：

你的通知逻辑写好了，但你不想让它作用于所有方法。

你只想让它在 com.example.service 包下的所有方法上生效。

这时候就需要切入点表达式：

@Pointcut("execution(* com.example.service..*(..))")
public void serviceMethod() {}

这段表达式翻译成大白话就是：

com.example.service 包及其子包下的所有方法，全部纳入这个切面的管理范围。

切入点就是一个匹配规则。

没匹配上的方法，切面逻辑根本不会生效。

目标对象（Target）和代理对象（Proxy）

到这里，你可能有个疑问：

切面、通知、切入点都配好了，那 AOP 到底是怎么"插入"到原有代码里的？

答案就是：它根本没改你的代码，而是偷偷换了一个对象。

这就是 AOP 最核心的机制——动态代理。

**目标对象（Target）**就是你原来写的业务类。

它是真正承载业务逻辑的地方。

切面不会修改它的源码，只是在运行时给它"套一层壳"。

打个比方：

目标对象是一台手机，代理对象就像手机外面套了一层保护壳。

你操作手机时，其实先经过保护壳，再到手机本身。

**代理对象（Proxy）**是 AOP 最关键的概念，没有之一。

Spring AOP 的运行机制是：用代理对象替换掉原始的目标对象。

调用方以为自己在调用目标对象，实际上调用的全是代理对象。

代理对象收到请求后，先执行通知逻辑，再决定是否调用目标方法，最后再执行后续通知。

从调用方的角度看，代理对象和目标对象长得一模一样——接口、方法签名完全一致。

但实际上，中间已经多了一层"加工"。

Spring AOP 中常见的代理创建器有：

  • AnnotationAwareAspectJAutoProxyCreator
  • InfrastructureAdvisorAutoProxyCreator
  • DefaultAdvisorAutoProxyCreator

实际开发中你不用手动配置这些，Spring 会自动注册。

你要做的只是：定义切面、写好通知、配好切入点。

那除了这些，还有一个相对冷门的概念叫引入（Introduction）。

引入可以在不修改目标类源码的情况下，让代理对象额外实现新的接口和行为。

打个比方：

你公司有个普通员工，某天你直接给他加了个"项目经理"的头衔。

他原来的工作照旧，但多了一种新身份。

这个功能实际项目中用得不多，但面试如果被问到，知道有这么个东西就行。

AOP 底层是怎么跑起来的？

到这里，AOP 的概念层面基本讲完了。

但如果你想把面试答深，一定要补上这一层：

AOP 的实现依赖动态代理，而动态代理的创建有两种方式——JDK 和 CGLIB。

代理方式 触发条件 实现原理
JDK 动态代理 目标类实现了接口 运行时生成接口代理类，通过 InvocationHandler 反射调用目标方法。
CGLIB 代理 目标类没有实现接口 基于继承，运行时生成目标类的子类，通过方法覆盖实现增强。

那问题来了——Spring 到底选哪种？

在 Spring Framework 早期版本中，默认策略是有接口使用 JDK，无接口使用 CGLIB。

但 Spring Boot 2.x 之后，默认使用 CGLIB 代理（等价于开启 spring.aop.proxy-target-class=true）。

说人话就是：

JDK 代理是"按合同办事"——你实现了什么接口，代理就帮你实现同样的接口；

CGLIB 是"继承增强"——运行时生成目标类的子类，通过方法覆盖实现增强。

从源码看代理是怎么创建的

很多人面试讲到"动态代理"就结束了，但这只答了表面。

如果你能把 Bean 的生命周期和 AOP 代理的创建过程串起来讲，面试官会觉得你是真的看过源码。

整个流程可以拆成以下几步：

  1. Spring 容器启动，按照依赖顺序创建 Bean
  2. Bean 实例化并完成初始化后，会进入 BeanPostProcessor 的后置处理阶段，AOP 就是在这里判断是否需要创建代理
  3. AnnotationAwareAspectJAutoProxyCreator 作为后置处理器，检查当前 Bean 是否需要被代理
  4. 如果需要代理，调用 AbstractAutoProxyCreator.createProxy() 方法
  5. 通过 ProxyFactory 获取代理对象
  6. 根据目标类是否实现接口，选择 JDK 动态代理或 CGLIB 代理
  7. 代理对象创建完成，替换原始 Bean，放入 Spring 容器

关键的源码链路：

BeanPostProcessor.postProcessAfterInitialization()
  -> AbstractAutoProxyCreator.wrapIfNeeded()
    -> AbstractAutoProxyCreator.createProxy()
      -> ProxyFactory.getProxy(classLoader)
        -> CglibAopProxy.getProxy()     // CGLIB 方式
        -> JdkDynamicAopProxy.getProxy() // JDK 方式

注意 wrapIfNeeded() 这个名字——"如果需要，就包装"。

也就是说，不是所有 Bean 都会被代理。

只有命中了切面匹配规则的 Bean，才会走代理创建流程。

这就是为什么 AOP 不会影响没有切面配置的业务 Bean—— 没有匹配到切面的 Bean 不会创建代理，因此不会产生运行时代理调用开销。

声明式事务：AOP 最典型的应用场景

如果你有余力，还可以把 Spring 声明式事务的执行流程也串进 AOP 的回答里。

因为 @Transactional 注解之所以能让方法自动拥有事务能力，靠的就是 AOP 代理在方法执行前开启事务、执行后提交或回滚。

整个流程大致是：

  1. 方法调用被事务切面拦截
  2. 事务拦截器在目标方法执行前，根据传播机制获取或创建事务
  3. 目标方法执行
  4. 正常返回 → 提交事务
  5. 抛出异常 → 回滚事务

这部分面试时可以根据自身掌握程度选择性回答。

能说清楚 AOP + 动态代理就已经足够应对大部分场景；

如果能顺带提一句声明式事务，那就是加分项。

小贴士

  • AOP 只代理 Spring 容器管理的 Bean，通过 new 关键字创建的对象不会被代理
  • 同类方法内部自调用不会触发 AOP，因为自调用走的是 this，绕过了代理对象
  • 环绕通知是唯一能阻止目标方法执行的通知类型，慎用
  • JDK 代理和 CGLIB 在现代 JVM 上性能差异极小，不用过度纠结
