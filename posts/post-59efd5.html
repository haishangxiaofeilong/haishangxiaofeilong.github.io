Agent 的短期记忆：三种 checkpointer 和一个 thread_id

2026-09-23 2715 字— 次阅读

跟 Agent 聊天，它能把前面聊过的内容接上，靠的是短期记忆。

新开一个会话，之前聊过什么它一概不知；

同一个会话里接着问，它能顺着上下文往下答。

差别就在短期记忆上。

它保存会话内的交互信息，Agent 给回复的时候，基于保存下来的历史信息作答，答出来的内容更贴合当前的对话。

这篇拆三件事：

短期记忆是什么、存在哪，以及怎么访问和修改记忆。

短期记忆是 state 的一部分

LangChain 对短期记忆的核心设计，是把记忆放进 state 里，由框架统一管理。

具体来说，短期记忆不挂在 Agent 流程外面当附加组件，它深度集成在 create_agent 的工作流里，作为 agent state 的一部分被自动管理。

不要把它理解成一个额外的功能模块。

它就在 Agent 的执行流程里面，流程走到哪，state 跟到哪。

给短期记忆下个定义：

在一个会话内，也就是一个 thread 内，让 Agent 记住并且利用之前的交互信息，实现上下文连贯的对话。

上下文指的是，打开一个聊天窗口之后，前后所有的历史交互信息。

这些历史信息默认放在 state 的 messages 字段里。

state 是框架统一管理的状态对象，除了 messages 还可以装别的字段。

三种 checkpointer，对应三种存储位置

使用上很简单，给 Agent 挂一个 checkpointer，由它负责把状态存下来。

常见的 checkpointer 有三种，存的位置不一样，适合的场景也不一样。

checkpointer 存储位置 适合场景 注意点
InMemorySaver 内存 日常写代码、开发调试 服务重启之后数据丢失
SqliteSaver 本地 SQLite 数据库 个人小型项目 生产环境不建议用
PostgresSaver PostgreSQL 数据库 生产环境 需要单独部署和维护 PostgreSQL

InMemorySaver 把状态放在内存里，使用最简单，日常写代码或者练习基本就用它。

代价是数据在服务重启之后就丢了。

SqliteSaver 把状态存进一个本地 SQLite 数据库文件，个人小型项目可以用。

正式的生产环境不建议，通常会用 PostgreSQL 这类单独部署的数据库。

PostgresSaver 背后是 PostgreSQL 数据库，生产环境常用，支持多实例共享状态，代价是这套数据库要单独部署和维护。

学习和工作的不同场景，切换对应的 checkpointer 就行。

thread_id 充当会话的身份证

挂上 checkpointer 之后，Agent 靠 config 里的 thread_id 定位当前会话的持久化状态。

写法长这样：

config = {"configurable": {"thread_id": "thread_123"}}

# 调用 agent 时把这个 config 传进去
agent.invoke({"messages": [{"role": "user", "content": "..."}]}, config)

thread_id 直接翻译是线程 ID。

跟大模型对话不会只开一个会话，可能同时开着好几个会话。

有了 thread_id，相当于给每个会话绑定了标识。

同一个 thread_id 内的历史信息保持一致，不同的 thread_id 各管各的。

thread_id 充当会话的身份证，把不同会话的记忆隔开。

thread_id 如果用错了，本来该分开的两个会话就可能共用同一个 thread。

比如一个 thread 先在聊旅游路线，接着又拿它聊美食，两段历史混在同一份列表里，模型回答美食问题时可能看到一串旅游记录，答案容易被带偏。

修改 messages 列表的两种常见方式

短期记忆中的对话历史，主要落在 state 的 messages 列表里。

要修改这个列表，常见的方式有两种。

最推荐的是中间件：

创建中间件，在 Agent 运行前或者运行后，往 state 的 messages 里添加、删除消息，或者修改其中某条的内容。

中间件操作的还是 state，参数传进来的时候，就能拿到列表里的信息。

也可以在工具里更新。

工具执行的时候能读到 state，把要改的内容放进返回结果，框架收到后合并进 state，实现对记忆的间接修改。

除这两种之外，其实还有一种做法，只是不推荐：

调用 agent 之后，从返回值里拿到 state 直接改。

这种改法绕开了框架的状态更新流程，改的只是手里那份对象，记忆里存的内容不会跟着变，对记忆来说等于什么都没改。

列表一直涨，上下文装不下

同一个会话里对话轮数多了之后，messages 列表会一直增长，有可能超过模型的上下文空间。

上下文变得非常庞大之后，生成的内容质量可能跟着下降。

列表里保存的信息太多，互相干扰，输出可能越来越差。

处理方式，官网列了四种：

处理方式 做法
截断 删掉最先或最后 n 条消息
删除 把指定的消息从列表里去掉
总结 把旧消息压成摘要
自定义策略 按自己的规则清理

短期记忆就聊到这，它只管一个 thread 内的事。

出了会话，就是长期记忆的事了，我们下篇单独讲。
