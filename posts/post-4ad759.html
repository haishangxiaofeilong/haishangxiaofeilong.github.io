Decode 每轮都重算一遍历史 token 吗：聊聊 KV cache

2026-09-09 2913 字— 次阅读

Decode 每一轮只冒出一个新 token。

可要算出这个 token，模型得拿前面所有 token 的 K 和 V 一起参与注意力计算。

这些 K 和 V 要是每轮都重新算一遍，Decode 就慢得没法看了。

所以它们被存进了一个地方，叫 KV cache。

我在《大模型推理的两阶段：一次 Prefill，加上多次 Decode》里讲过，Prefill 只跑一次、Decode 要跑很多次；

我在《一次完整推理，模型背后要走完 5 道工序》里也带过，调度阶段会先把 KV cache 的空间安排好，Prefill 算完再把 K 和 V 写进去。

这篇就把它讲透：

注意力为什么非要 Q、K、V 这三样东西，两个阶段各自怎么用这块缓存，以及不缓存会怎么样。

注意力层里真正在算的是 Q、K、V

大模型里有一层一层的注意力层，每一层都要算 Q、K、V 这三样。

说白了，它们都是向量，由同一个输入向量乘上不同的权重矩阵得到。

Q 是当前这个 token 发出的提问，问的是该去关注谁。

K 是每个 token 挂出来的标签，写着自己这儿有什么、值不值得关注。

V 才是真正被取走的信息。

举个通俗一点的例子，就像你去图书馆查资料。

Q 是你手上的问题，K 是书脊上的分类标签，V 是书里真正的内容。

你拿问题去和一排标签比对，对得上的多取一些，对不上的少取一点。

Q 和 K 比对出来的匹配程度，决定了每个 V 被取走多少。

Q 每次只来一个，K 和 V 却越攒越多

那问题来了：

Prefill 和 Decode 的时候，Q 分别是谁？

Prefill 阶段，Q 是整段提示词切出来的所有 token，比如一次来 4 个。

到了 Decode，每一轮只有一个 Q。

Prefill 处理完提示词后，可以根据最后一个位置的输出得到第一个生成 token；

之后每一轮拿上一步生成的 token 作为输入，预测下一个 token。

K 和 V 走的是另一套节奏。

要算当前这个 token 的注意力，就得拿到它自己和前面所有 token 的 K 和 V。

所以 Prefill 算完，这 4 个 token 的 K、V 就进了 KV cache。

Decode 每生成一个新 token，就把这个新 token 的 K、V 也追加进去。

缓存是累增的，像记账一样只往上添一行，不会把前面的账重新算一遍。

生成 EOS 后，这个请求通常就结束了，不再继续追加。

对新请求来说，Prefill 写入，Decode 边读边加

这也是两个阶段对 KV cache 最不一样的地方。

对一个没有命中已有 KV cache 的新请求来说，Prefill 把整段提示词一次性送进模型，跑一遍前向计算，顺手把每层算出来的 K、V 写进缓存。

这一步不需要从 KV cache 读取历史 K、V，因为对这个请求来说，缓存一开始还是空的；

注意力要用的 K、V，是这一遍前向刚算出来的。

Prefill 只跑一次。

Decode 要跑很多次，每一轮的活都一样：

拿当前这一个 token 的 Q，去缓存里把历史的 K、V 全读出来算注意力，得到下一个 token，再把这个新 token 的 K、V 写回去。

阶段 对 KV cache 做什么 Q 的规模 跑几次
Prefill 写入 K、V 整段提示词的全部 token 1 次
Decode 读取历史 K、V，并追加当前 token 的 K、V 每轮 1 个 token 很多次

不缓存会怎样：每轮都要把历史重算一遍

Q、K、V 是怎么来的？

在某一层注意力里，输入隐藏状态 X 会分别乘上三个权重矩阵：

X 乘 WQ 得到 Q，X 乘 WK 得到 K，X 乘 WV 得到 V。

在自回归生成的因果注意力里，历史位置的隐藏状态不会因为后面来了新 token 而重新变化，WK 和 WV 也没变。

所以历史 token 在这一层算出来的 K 和 V，每一轮都是一模一样的值。

既然结果不会变，就没必要每轮重新计算，直接缓存下来就行。

不缓存的话，Decode 每一轮都得重新计算前面所有 token 对应的隐藏状态，再乘一遍 WK、WV，把同样的 K、V 重算出来。

Prefill 只做一次，重算的代价还有限；

Decode 要一轮一轮跑，重复的计算全堆在这儿。

所以 KV cache 存在的理由非常直接：

把已经算过、后面还要反复用的历史 K/V 存下来，避免 Decode 每一轮重新计算它们。

Decode 每一步省下多少时间，最后会落到相邻 token 之间的时间间隔上，《大模型推理的两个速度指标：TTFT 和 ITL 分别卡在哪一段》里拆的就是这个指标。

先按单头理解，别一上来就想多头

看到 Q、K、V，很多人会立刻想到多头注意力，然后开始绕。

其实不用。

你先用单头把"Q 去匹配 K、再取走 V"这件事想明白就够了。

多头只是把这件事并行做上好几遍，每一头关注的角度不同，最后把各头的结果拼起来。

理解 KV cache 的时候，按单头想完全够用。

顺带说一句，这块缓存为什么会占那么大显存：

每个 token、每一层，都要存下自己的 K 和 V。

token 越长、层数越多，它就越大。

所以长上下文和高并发请求，都会明显增加 KV cache 的显存压力。

这块缓存，最后是推理引擎在管

在实际部署里，KV cache 的空间分配、写入和读取，主要由推理引擎负责管理。

推理引擎要把 Prefill 和 Decode 分别实现，还要决定同一时刻涌进来的一大堆请求怎么排、怎么凑在一起跑。

对企业来说，同一时刻往往是很多个客户端一起在问。
