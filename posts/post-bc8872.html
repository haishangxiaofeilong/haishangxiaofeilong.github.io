MySQL网络面试题

你建表时引擎那栏从没改过，可 InnoDB 凭什么把 MyISAM 挤成了老古董？

2026-08-25 2739 字— 次阅读

建表的时候，引擎那一栏你大概率从没改过，因为从 MySQL 5.5 开始，InnoDB 就是默认存储引擎；

到了现在的 MySQL 版本，它依然是默认且官方推荐的通用型引擎。

可你翻老项目，偶尔还能看到 MyISAM。

这俩名字总被放在一起比，面试也常问到。

其实它们不是谁替代谁的关系，只是解决的问题侧重不同：

InnoDB 是通用型存储引擎，重点解决事务、并发和可靠性问题；

MyISAM 是更早的存储引擎，因为采用表级锁，更适合读多写少甚至只读的场景。

那区别具体在哪？

我从事务、锁、索引三个维度拆开讲。

事务：InnoDB 有，MyISAM 真没有

这一条是最根本的分水岭。

InnoDB 支持事务，有完整的隔离级别，并通过事务机制以及 redo log、undo log 等机制提供持久性、回滚和崩溃恢复能力。

MyISAM 不支持事务，也没有事务隔离级别和事务回滚能力。

对比项 InnoDB MyISAM
事务支持 支持，有隔离级别 不支持，无隔离级别和回滚能力
事务日志 有 redo log、undo log 没有事务日志
外键 支持 不支持

为什么这一条这么关键？

转账就是最典型的场景：

从 A 账户扣钱、给 B 账户加钱，这两步必须绑成一个事务。

用 InnoDB，要么都成功，要么都回滚，钱不会凭空消失也不会凭空出现。

换成 MyISAM，扣完 A 还没来得及给 B 加的时候数据库崩了，结果就是 A 的钱没了、B 也没收到，账目直接对不上。

锁：InnoDB 能锁到行，MyISAM 一锁就是整张表

并发场景里，锁的粒度直接决定同一时间能扛多少人一起改数据。

InnoDB 支持行级锁，也支持表级锁。

它的行锁本质上是基于索引记录加锁的：

查询条件命中合适索引时，可以只锁住需要处理的索引记录；

如果没有合适索引，UPDATE 或 DELETE 可能需要扫描大量甚至全部记录，从而锁住大量记录，严重影响并发。

MyISAM 采用表级锁，写操作通常需要锁住整张表，读写之间容易产生锁竞争；

不过在满足条件时，MyISAM 也支持并发插入，允许 INSERT 与 SELECT 并发执行。

对比项 InnoDB MyISAM
锁类型 行级锁 + 表级锁 只有表级锁
锁的触发 行锁基于索引记录，无合适索引时可能锁大量记录 写操作触发表级锁
并发控制 支持 MVCC，普通读通常不阻塞写 读写之间有锁竞争

表级锁的感觉，就像把整个厕所的门锁了，一个人进去，剩下所有人都得在门外等；

行级锁更像只占一个隔间，别人还能用别的隔间，彼此不耽误。

InnoDB 还有个杀手锏叫 MVCC（多版本并发控制），它让普通一致性读可以按照事务的可见性规则读取合适的数据版本，因此普通读通常不会因为其他事务正在修改数据而被阻塞。

MyISAM 没有 InnoDB 这样的 MVCC 机制，普通读写之间更容易受到表级锁影响。

索引：一个把数据塞进叶子，一个只存行指针

这一节最容易绕晕，但也最能体现两者设计的差别。

InnoDB 既有聚簇索引，也有二级索引。

聚簇索引的叶子节点直接存整行数据；

二级索引的叶子节点存的是主键值，所以走二级索引查非主键字段时，得先拿到主键，再回表去聚簇索引里找那一行完整的记录。

MyISAM 只有非聚簇索引。

不管是主键索引还是普通索引，叶子节点存的都是数据文件中的行指针（位置），可以理解为指向数据文件中对应记录的位置。

拿到行指针，直接去数据文件里把那一行捞出来就行，没有"回表"这回事。

对比项 InnoDB MyISAM
索引类型 聚簇索引 + 二级索引 只有非聚簇索引
索引存储 聚簇叶子存整行；二级叶子存主键值 叶子统一存数据文件中的行指针（位置）
回表 二级索引查询需要其他非索引列时需要回表 不回表，按行指针直接读取
主键要求 不强制建主键，但建议使用；无主键时选唯一非空索引，都没有则生成隐藏的 6 字节行 ID 无主键要求，主键索引也只是普通索引

MyISAM 的叶子只存行指针，相当于书的书签直接标了页码，翻到那一页就看到了内容。

InnoDB 的二级索引叶子只存主键，相当于书签上写的是"见第 5 页主条目"，还得再翻一次才能看到正文，这就是"回表"的由来。

这里有个容易忽略的细节：

InnoDB 不要求表必须显式定义主键，但如果没有主键，它会选择一个合适的唯一非空索引作为聚簇索引；

如果连这样的索引也没有，InnoDB 会生成一个隐藏的 6 字节行 ID 作为聚簇索引。

MyISAM 没有 InnoDB 那种聚簇索引，主键索引和普通索引在存储结构上都属于非聚簇索引，索引叶子节点保存指向数据记录的行指针。

怎么选：现在基本不用纠结

放到今天的业务里，这个问题其实没那么让人头疼。

InnoDB 适合电商、金融、支付这类既要高并发写入、又要事务保证一致性的场景。

MyISAM 更适合读多写少甚至只读的场景，例如一些老系统中的报表或静态数据表；

但不能简单理解为"MyISAM 读性能一定比 InnoDB 高"。

不过你打开现在的大多数新项目，默认使用的基本都是 InnoDB，新系统基本没有理由特意去换 MyISAM。

搞清楚它俩的区别，更多是帮你在面试被问到、或者排查老系统问题时心里有底。
