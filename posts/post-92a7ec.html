LangChain 工具调用出错：自动重试和自定义中间件，到底该用哪个

2026-09-21 3495 字— 次阅读

Agent 跑起来之后，干活靠的是调工具。

工具不一定每次都调用成功。

网络抖一下，接口被限流，模型拼出来的参数也可能不合规矩。

所以，出错很正常，关键在于出错之后怎么办。

处理的核心思路就是：

把会中断执行的异常，换成模型能读到的一条错误信息。

模型读到这条信息，就有机会自己修正，Agent 的流程也能接着往下走。

在思想层面，这和你写传统业务代码时用 try catch 接异常是一回事。

到了工具调用这一层，LangChain 把这类处理交给了中间件。

中间件可以把一段额外的逻辑包在工具执行的环节外面。

错误在这里被拦下来、被转换，模型那头收到的，是一条描述工具错误的 ToolMessage，流程不会在这里断掉。

框架自带的重试中间件

有一类错误是瞬时性的，错一次不代表次次错。

网络抖动，过一会儿自己就好了。

外部 API 被限流，隔一会儿再试就通了。

对付这类错误，重试是最直接的办法。

LangChain 提供了一个现成的中间件，叫 ToolRetryMiddleware，传给 create_agent 就能生效：

from langchain.agents import create_agent
from langchain.agents.middleware import ToolRetryMiddleware

agent = create_agent(
    model=model,
    tools=[search_tool],
    middleware=[
        ToolRetryMiddleware(
            max_retries=3,
            initial_delay=1.0,
            backoff_factor=2.0,
        ),
    ],
)

工具执行失败，中间件按配置的策略自动多试几次，不用你自己写重试循环。

常用的参数有六个，各管一件事：

参数 管什么 默认值
max_retries 最多重试几次 2，加上首次调用一共 3 次
initial_delay 第一次重试前等多久，单位秒 1.0
backoff_factor 退避因子，控制等待时间的增长倍数 2.0
retry_on 对哪些异常才重试 框架内置的一套判断
on_failure 重试用完还是失败时怎么办 把错误写成一条 ToolMessage 返回
tools 只对哪些工具生效 全部工具

除了这六个之外还有两个：

  • max_delay 给单次等待封顶，默认 60 秒；
  • jitter 控制要不要给等待时间加随机量，默认开启。

backoff_factor 定的是指数退避的节奏。

按上面的配置算，等待时间的理论值是第一次重试前等 1 秒，第二次等 2 秒，第三次等 4 秒，一轮比一轮长，免得给本就出问题的服务再添压力。

实际等待会在这个数字上浮动，因为 jitter 默认开着，每次等待都会加上一点随机量，避免多个调用挤在同一时刻一起去重试。

retry_on 和 tools 负责收窄重试的范围。

retry_on 决定对哪些异常才重试，想自己定就传一组异常类型进去，或者传一个函数，它拿到抛出来的异常，返回 True 就重试，返回 False 就不重试。

tools 决定重试挂在哪几个工具上，不传就是对全部工具生效。

on_failure 管的是重试次数用完、仍然失败的那一刻。

默认行为是把错误详情写进一条 ToolMessage 返回，Agent 继续跑；

设成 "error" 则把异常重新抛出，这次执行就停在这里；

也可以传一个函数，最后那条错误信息写什么，由它说了算。

ToolMessage 是 LangChain 里表示工具结果的消息对象。

工具执行成功时，结果是它；

出错时，那条错误说明也是它。

重试解决的是执行时机的问题。

参数本身传错了，重试多少次结果都一样。

业务逻辑里出的问题，多跑几次也不会有所改变。

重试解决不了的，交给自定义中间件

自定义走的是 wrap_tool_call 这个装饰器，同样从 langchain.agents.middleware 里导入。

它把你写的函数挂到工具执行的环节上，工具每次执行都会先经过这个函数。

函数拿到两个东西：

request 是这次调用的请求，里面带着调用的 id、工具名和参数；

handler 是执行工具的动作，调一下它，工具才真正跑起来。

处理错误的逻辑就两步：

调用 handler 时接住异常，返回一条带错误说明的 ToolMessage。

from langchain.agents.middleware import wrap_tool_call
from langchain_core.messages import ToolMessage


@wrap_tool_call
def handle_tool_error(request, handler):
    try:
        return handler(request)
    except Exception:
        return ToolMessage(
            content="调用工具出现错误，检查参数以及执行逻辑",
            tool_call_id=request.tool_call["id"],
        )

对着代码看：

try 里调 handler(request)，工具正常跑完就正常返回。

一抛异常，except 把它接住，返回一条 ToolMessage。

content 是给模型看的那句说明，告诉它工具出了错，往参数和执行逻辑这两个方向检查。

tool_call_id 从 request.tool_call 里取。

模型发起了哪次调用，这条错误就得挂回哪次调用上，对上了号，模型才知道是哪个工具出了问题。

这条 ToolMessage 会作为工具的结果回到模型那里。

模型读到错误说明，就有机会修正参数，再调一次，实在处理不了再向用户反馈。

流程到这里没有断，错误变成了一条模型能拿来用的信息。

实际工作里，这种写法用得比自动重试更多。

瞬时性错误交给重试就够了。

剩下的错误五花八门，业务逻辑里抛出来的、依赖服务返回的，处理办法各不相同，自己写的中间件里怎么处理是由你来定的，灵活得多。

有一类错误到不了这个中间件：

工具参数没通过校验的。

这类错误在工具真正执行之前就被处理掉了，会直接变成一条错误信息回到模型那里。

两种方式怎么挑

对比项 ToolRetryMiddleware wrap_tool_call 自定义中间件
来源 框架自带 自己写
适合的错误 瞬时性错误，网络抖动、API 限流 工具执行中抛出的业务异常
处理动作 按退避节奏自动多试几次 接住异常，返回一条错误 ToolMessage
灵活性 在参数里配 逻辑自己定

面试被问到工具调用出错怎么处理，把这两条说出来就够了。

两条路最后都能把工具执行的失败，转成模型能拿到的反馈。

区别在于，重试几次、失败之后怎么办，ToolRetryMiddleware 都做成了参数；

自定义中间件里，拦不拦、重不重试、返回什么，都是你自己写。
