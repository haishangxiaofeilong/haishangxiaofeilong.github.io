Skill 上线之后，怎么知道它悄悄退化了？

2026-09-02 2929 字— 次阅读

你写了个 Skill，本地测着挺顺，就让它上岗了。

结果一周后，有同事跑来说：

你那个东西把我项目整个重搭了一遍。

你这才反应过来，它早就不对劲了，只是你一直没察觉。

问题不在 Skill 写得好不好。

在你根本没有任何办法，知道它已经退化。

每次你动它一下，哪怕只是改一句提示词、加一个工具，它的行为边界都可能跟着漂。

等它接进真实工作流，还会自己生成文件、留下副作用。

你改一个角，别处已经悄悄变了。

维护一个 Skill，写复杂谁都会。

难的是，你能靠什么持续知道它没出问题。

别拿体感当验收

很多人所谓的维护，就是每次改完跑一下，没报错就算过了。

这叫信感觉，不叫有证据。

第一步永远是先把什么叫好写下来，再谈写测试。

靶子都没有，后面所有评估都是空的。

验收其实看四个地方。

一层看结果对不对。

任务达成了吗？

应用能跑起来吗？

这一层最直观，也最容易被当成全部。

但只看结果远远不够，一个 Skill 可能兜了一大圈把事办了，走的路径你完全没料到，换个输入它就不一定还能走通。

另一层看过程对不对。

该轮到这个 Skill 出场的时候，它有没有被正确选中？

被选中之后，又是不是按预期的步骤和工具链在执行？

有没有执行多余操作、产生本来不该有的副作用？

这一层盯的是行为路径本身，终点只是其中一环。

还有两维总被人漏掉。

一是产物能不能被下游接住：

输出符合你的规范吗？

文件结构、代码风格对不对？

风格不一致不影响它跑不跑得通，但真实工作流里，下游的人或系统会直接拒收。

二是执行成本有没有失控：

有没有跑没必要的命令、做重复的检索，白白烧掉 token 和时间？

单次测试你感觉不到，接进生产大量触发后，这点浪费会被放大成真金白银。

这四件事合起来，干的是同一件事：

把验收的对象，从最后长得像不像，推进到中间到底发生了什么。

它会从两个地方出问题

这里有个容易忽略的点：

Skill 有两个需要分别维护的面。

一个是执行体，包括指令、工具、步骤以及相关资源，它具体怎么干活。

一个是触发边界，也就是 Agent 根据 Skill 的名称、描述等元信息和当前上下文，判断什么时候该轮到它出场。

打个比方。

执行体像后厨的菜谱，教厨师一步步怎么做菜；

触发边界像门口的招牌，写明什么情况下该点这道菜。

两套东西是分开的：

菜谱改了，招牌不会自动跟着变；

招牌上的品类改了，菜谱也不会自动变。

正因为两套分开，两面会分别退化。

你改了指令，触发边界没碰，可 Skill 的行为已经变了。

你改了 description，执行体没碰，可触发范围飘了。

你要是只盯执行体，触发边界那边退化了，你也根本发现不了。

每个面都会出自己的问题

先看触发边界。

触发边界模糊了

哪些提示词明明该触发它，却没触发？

哪些只是相邻需求，却把它误触发了？

比如你只是想给现有项目加个样式。

如果这请求本来不该轮到它，它却被错误选中，说明触发边界已经模糊。

边界一模糊，Skill 就会在不该出手的时候出手，生产里非常危险，因为它会动你本来没打算动的东西。

反过来，如果它本来就该被选中，只是在执行时把整个项目的目录结构都重排了，那问题就出在执行体——它选得没错，只是干过头了。

再看执行体，它最容易犯两类错。

踩了环境的坑

Skill 会不会默认自己永远跑在空目录里？

它又是不是默认系统里一定有某个包管理器？

这类假设在本地测试时几乎不暴露，因为你的本地环境刚好满足了这些前提。

可换一台机器、换一个用户，前提就可能全部失效。

环境假设往往是最隐蔽的一类失控，它不在 Skill 的代码里，在它的运行上下文里。

顺序错了

Agent 会不会跳过安装依赖，因为它误以为依赖已经装好？

会项目都还没建出来，就先去配置别的东西吗？

这类失控的特点是，每一步单独看都是对的，但顺序错了，整个执行就卡在某个中间状态。

很多时候结果看着还行，可其中一条路径已经在悄悄退化。

把失控点钉成一套样本

找到这些失控点之后，下一步是把它们钉死成一套回归样本。

最容易犯的错，是一上来就想搞个很大的基准测试。

对边界相对清晰的单个 Skill 来说，起步阶段不一定需要很大的基准集，先用十几条高价值样本把典型失败模式卡住，往往比堆几百条普通样本更有效。

正向样本可以先覆盖三种典型场景。

一种是点名它，直接把 Skill 名字写出来，保证改了描述和指令之后，显式调用这条路径仍然稳。这是最基础的防线。

一种是只说场景，不提名。用户不提 Skill 名字，只描述要解决的场景，看 Agent 能不能自己选中它。这类测的是触发边界的质量。

还有一种是混入噪声，在真实业务上下文里加入无关信息，测的是 Skill 在嘈杂环境下，还能不能被正确识别和执行。

还有一类最容易被忽略，但它最危险：负样本。

它不问 Skill 会不会被触发，它问的是该不该被触发。

你本想做个增量改动，这活儿压根不归它管，它却认定该自己上、抢着出场。

负样本是在给 Skill 画边界，不只验证它能做什么，还要验证它知道什么时候别动。

训练新人也是这个理：

不光要考他该做什么，更要考他什么时候别动。

知道什么不该做，比知道该做什么更值钱。

样本建好，维护才真正开始。

每次你改动 Skill，都重新跑一遍这套样本。

不要求每次输出一字不差，只看那些已经被验证过的关键行为，有没有出现不该出现的行为漂移。

这一步，才把“它有没有退化”，落到了可以前后对比的证据上。

你完成的是一件更基础的事

把这套样本建起来，你真正完成的是一件比评估系统更基础的事：

把靠体感维护，换成靠最小证据维护。

这个转变比任何工具细节都重要。

因为 Skill 一旦接进生产，它就不再只是提示词技巧，它开始变成一个要被持续验证的工作流资产。

下次再写 Skill 之前，先想清楚三件事：

你想让它做成什么？

它在哪些地方会失控？

你准备用哪些样本，持续盯住这些失控点？

想清楚这三件，你才算真正从会写一个 Skill，走到了会维护一个 Skill。
