Agent 的长期记忆：一个 Store，装下跨会话的信息

2026-09-24 2217 字— 次阅读

我在《Agent 的短期记忆：三种 checkpointer 和一个 thread_id》里讲过，短期记忆只管一个 thread 内的事，出了会话就不认了。

长期记忆接的是会话之外的那一层。

它保存跟特定用户或者应用相关的全局信息，比如用户偏好、固定属性、关键的历史信息。

差别用两个会话就能看出来：

在 A 会话里记下几条属性，存进长期记忆；

换到 B 会话，还能把它们取出来接着用。

短期记忆做不到这一点，它只在当前会话或者当前 thread 里有效。

再比如，对话轮数一多，历史信息会攒下很多，不可能全都放进短期记忆。

其中有些信息以后换个会话还会用到，这类就该放进长期记忆。

短期记忆是这次对话的上下文，长期记忆是 Agent 跨会话留下来的信息。

它跨会话保留，独立于任何一次具体对话而存在，需要的时候可以把相关信息召回。

这篇就拆五件事：

长期记忆是什么、交给谁管、存在哪、按什么结构组织，以及怎么读写。

长期记忆由谁来管

LangChain 里，长期记忆由 Store（存储）组件负责管理。

用法跟短期记忆很像：

创建一个 Store 实例，把它传给 create_agent。

上篇讲短期记忆的时候用的是 checkpointer，这一步用的是 Store，思路是一样的。

Store 有多种实现，先看最常用的两种。

两种常见的 Store：内存和 PostgreSQL

Store 存在哪 适合场景 注意点
InMemoryStore 内存 开发调试 服务重启之后数据丢失
PostgresStore PostgreSQL 数据库 生产环境 数据库要单独部署和维护

InMemoryStore 把数据存在内存里，写代码、调试的时候用它最省事。

代价是服务一重启，存下来的东西就没了。

PostgresStore 背后是 PostgreSQL 数据库，数据能持久保存，生产环境用它更合适。

代价是这套数据库要单独部署和维护。

如果只是写点代码、跑个 Demo，用 InMemoryStore 就够了；

要做一个生产系统，就该换成 PostgresStore 这类数据库后端。

把读写封装成工具

在 Agent 里，一个常见做法是把长期记忆的读写封装成工具。

工具的执行函数里能拿到一个 runtime 对象，Store 实例就挂在这个对象上，用 runtime.store 就能访问到。

记忆按命名空间和键分开存

存进去的数据按三部分组织：

命名空间、键、值。

命名空间像一个文件夹，用来把数据隔开，通常放用户 ID、应用上下文这类信息。

官方没有规定必须这么分，这只是一些常见的做法。

要让不同用户的记忆彼此隔开，就把用户 ID 放进命名空间。

键像文件名，用来定位命名空间里的某一条具体记忆。

值是一个 JSON 对象，存的是这条记忆的实际内容。

读用 get，写用 put

读一条特定的记忆，用 runtime.store.get，参数是命名空间和键：

runtime.store.get(("users", "user_123"), "profile")

写入或者更新一条记忆，用 runtime.store.put，在命名空间和键后面再补上要存的值：

runtime.store.put(("users", "user_123"), "profile", {"language": "中文"})

记忆多了，可以按语义搜

除了按键精确取，Store 还支持语义搜索，在一个命名空间里按意思去找相关的记忆，不用去凑关键词。

这个能力默认不开启，要先把 Store 配上向量模型，把存进去的内容建成向量索引。

记忆数量一大，语义搜索就很管用。

真实开发里，长期记忆和短期记忆是同时生效的。

用起来并不复杂：

设好命名空间、键、值，直接 get 和 put。

Store 解决的是记忆存在哪里，至于什么值得记、什么时候记、什么时候取，还是应用自己的事。

真正要想清楚的是：

哪些信息该留在会话里，哪些该放进长期记忆。
