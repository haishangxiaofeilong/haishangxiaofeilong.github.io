你调的接口几乎都返回 JSON，可它凭什么干掉了 XML？

2026-08-23 3179 字— 次阅读

你调过的每一个后端接口，返回的数据几乎都是 JSON。

你大概会觉得，这是因为 JSON 在技术上"天生最强"。

这个直觉是错的。

JSON 能赢，并不靠某项碾压级的技术指标，而是刚好踩中了 Web 开发最在意的三个点：

表示更紧凑、语法更简单、生态更广。

再往深一层说，是工程效率赢了严谨性。

一句话：

JSON 把"传输数据"这件事做到了极简，于是 Web 选了它；

但凡是"严格、复杂、要文档化"的场合，XML 依然稳坐钓鱼台。

同样一份数据，JSON 凭什么更短

先看最明显的差距。

还是那个用户：

名字张三，年龄 28，爱好篮球和阅读。

XML 会写成这样：

<user>
  <name>张三</name>
  <age>28</age>
  <hobbies>
    <hobby>篮球</hobby>
    <hobby>阅读</hobby>
  </hobbies>
</user>

每个字段名都要用一对开闭标签包起来，name 在文档里出现了两次——一次开头，一次结尾。

数据一多，这些重复的标签名就是纯纯的字节浪费。

换成 JSON：

{
  "name": "张三",
  "age": 28,
  "hobbies": ["篮球", "阅读"]
}

在这个例子里，每个字段名只需要出现一次；

数组则直接用 [] 表达，不需要为每个元素额外套一层标签。

打个比方，XML 像一份公文，每个信息都得用标准格式包起来；

JSON 更像一张便签，只写关键内容。便签自然比公文短。

这种简洁带来的好处，远不止"表示更紧凑"本身。

它让数据读起来像一组"键值对"，直接对应程序里的对象结构，人看得舒服，机器也省事。

为什么 JSON 通常更容易解析

体积小确实有帮助，但 JSON 通常更容易解析，更重要的原因是：

它的语法和数据模型都比较简单。

JSON 只有对象、数组、字符串、数字、布尔值和 null 六类值。

看到 { 可以进入对象，看到 [ 可以进入数组，其他内容则按照明确的语法规则继续解析，整体结构比较直接。

XML 的语法体系更丰富，除了元素和属性，还涉及命名空间、实体、CDATA、注释以及混合内容等机制。

这并不意味着 XML 不能高效解析。

XML 同样支持流式解析；

只是相比 JSON，解析器需要处理的语法和数据模型更加丰富。

如果使用 DOM，两者都会涉及把文档解析成内存中的树结构，文档越大，内存开销通常也越明显。

所以更准确的说法是：

JSON 和 XML 都能被解析，区别只是 JSON 的语法和数据模型更简单，在常见的数据交换场景下实现起来更轻量。

为什么 JSON 能迅速成为跨语言的通用格式

体积小、语法简单——这些特点，任何一门语言都能自己设计一套类似的格式。

JSON 真正厉害的地方，是几乎所有主流编程语言和开发生态都对它提供了成熟支持。

原因在于它的数据模型太通用：

对象、数组、几种基本类型——这正好是现代编程语言最核心的抽象。

JSON 的对象、数组和基本类型，与现代编程语言中的字典、列表以及基本数据类型有比较直接的对应关系。

XML 则更偏向文档和标记结构，映射成业务对象时，通常需要额外的解析或转换步骤。

Web 又推了一把。

浏览器中的 JavaScript 原生提供了 JSON.parse() 和 JSON.stringify()，JSON 与 JavaScript 的对象模型联系非常紧密，前后端用同一种格式对话，开发效率直接拉满。

等 Node.js 和 RESTful API 流行起来，JSON 顺理成章成了 Web 接口的默认选项。

一个生态如果缺少成熟的 JSON 支持，开发体验自然会受到影响。

XML 远没有到退休的时候

有些场合 JSON 顶不上去，XML 反而依然有明显优势。

金融行业的一些交易报文就是典型场景。

那种数据要求极其严格：

每个字段都得有明确定义、类型约束和校验规则，收发双方还得靠一份标准文档保证理解完全一致。

这时候 XML Schema 和命名空间的价值就出来了。

JSON 本身定义了基本的数据类型，但不像 XML 加 XML Schema 那样提供成熟的模式定义和强制校验体系。

实际项目通常需要借助 JSON Schema 或其他校验机制来约束数据结构。

再比如文档标记：像 .docx 这样的 Office Open XML 文档，内部大量使用 XML 描述段落、文本、样式等结构。

对于"文字内容和格式标记交错出现"这类混合内容，XML 的表达方式天然更合适。

还有数据转换场景，XML 有 XSLT 这样成熟的转换工具链；

在一些需要长期保存、跨系统交换和保持结构化语义的场景中，XML 也仍然有较成熟的应用基础。

一句话：

JSON 在"需要严格、复杂、文档化交换"的领域，并不比 XML 强。

一张表看清 JSON 和 XML

维度 JSON XML
表示形式 结构紧凑，键值对和数组表达直接 标签和属性表达更丰富，但通常更冗长
解析 语法和数据模型较简单，解析器实现轻量 语法体系更丰富，解析器需要处理的规则更多
类型与校验 内置基本类型；结构约束通常借助 JSON Schema 等机制 可结合 XML Schema 进行类型与结构校验
语言映射 与字典、列表等数据结构对应直接 更偏文档/标记结构，映射业务对象时通常需要额外规则
混合内容 不擅长表达文本与标记交错的文档结构 原生支持混合内容
典型场景 Web API、配置、数据交换 文档、复杂数据交换、部分行业标准报文

说到底，Web 选择了简单，而不是把严谨塞进数据格式

理解了上面的对比，再看 Web 为什么最终站队 JSON，答案就清楚了。

最根本的取舍是：

Web 更倾向于用"简单和效率"，而不是把"严格约束和丰富的文档能力"全部放进数据格式本身。

Web 开发讲究快速迭代、前后端分离，数据结构通常不复杂，大部分场景无非是把数据库里的记录原样丢给前端。

JSON 的设计非常克制，上来就是数据本身，所见即所得。

XML 本想解决更多问题——数据发布、可扩展标记——但这些"更强的能力"在 Web 接口这种场景里，反而成了负担。

技术世界里没有绝对的好坏，只有适不适合场景。

下次你理所应当地用 JSON 时，不妨想一想：

你要的到底是"轻快"，还是"严谨"？
