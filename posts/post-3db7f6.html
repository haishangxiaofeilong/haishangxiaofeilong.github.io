LangChain 的九个核心组件，各管什么？

2026-09-15 3383 字— 次阅读

拆开看，LangChain 日常开发里常用到的能力，可以归成九块。

组件 解决什么
模型 换模型的时候，上层代码不用跟着重写
消息 一场对话里，哪句话是谁说的，分得清
工具 模型够得着外部能力
智能体 多步任务里，下一步做什么由谁定
短期记忆 这一场对话里，前面说过的话带得上
长期记忆 换一场对话，它还认得你
流式处理 结果边生成边往外送，不用干等
结构化输出 程序能直接吃下模型的话
中间件 不改业务代码，统一加规矩

先搭起能跑的四块

一个应用要真能干活，核心就是这四块：

模型、消息、工具、智能体。

模型

大模型本身会输出文本，但应用要的不只是这个，还得能把它稳稳地调起来。

LangChain 在模型这一块做的事，就是提供一套标准化的推理接口：

不管换到哪家供应商，都按同一套方式调用。

最常用的调用方式有三种。

  • invoke，发一次请求，等一个完整结果
  • stream，结果边生成边往回送
  • batch，一次处理一批输入

好处是上层调用代码通常不用跟着大改，把模型的提供商和配置换一下就行。

各家接口的差异，都被这一块挡在外面。

消息

一场对话里，说话的不只是你和大模型。

有系统提前定下的规矩，也有工具返回的结果。

最常见的消息类型，可以先看这四种：

  • 系统消息，开场先定规矩，比如"你是一个客服助手"
  • 用户消息，人说的话
  • AI 消息，模型回的话
  • 工具消息，工具执行完返回的结果

好处是每条消息都标着角色，多轮对话的上下文边界分明，不会串。

哪句话是谁说的，归这一块管。

工具

模型关在自己的世界里，够不着外面。

工具组件就是给模型接上外部能力：

查数据库、调接口、搜网页。

写起来不复杂，在 Python 里，普通函数加上 @tool 就能定义成工具。

真正要交代清楚的有三样：

名字、描述、参数结构。

三样都重要，但描述尤其关键。

模型主要靠这三样判断：

这个工具是干什么的、什么时候该用、参数怎么填。

描述写得含糊，模型就容易挑错工具。

所以在真实项目里，可以让大模型帮忙生成描述初稿，再人工检查和验证。

自己练手的时候，可以省掉这一步，但用途和参数还是得说清楚。

模型够不够得着外面的世界，靠的就是这一块。

智能体

上篇《都是调大模型，为什么中间还要加一层 LangChain？》里讲过，大模型本身是被动的：

你问它，它回答你，答完就结束。

智能体不一样，它是个带循环的部件。

你把请求和目标交给它，它结合可用的工具，让模型判断下一步该调哪个、参数怎么填。

调完看结果，再判断下一步。

如此往复，直到任务完成，或者触发停止条件。

工具提供能力，智能体决定什么时候用、用哪一个。

再给它加上记性

短期记忆

一场对话里，前面说过的话得带着走。

大模型自己不会记，你不把历史带进这次请求，它就不知道刚才聊到哪。

短期记忆管的就是这件事。

它的范围是一条会话线程，也就是这一场对话。

在 LangChain 里，短期记忆是挂在 Agent 的状态上的，配一个保存器（checkpointer）就能存下来。

Agent 运行过程中会不断保存状态，下一次可以接着读。

对话长了，总有撑爆上下文窗口的时候。

常见的处理办法有三种：

截断、删除、总结。

也可以自己写策略。

存在哪儿也有讲究。

开发阶段用内存实现就够，重启丢了也无所谓；

上了生产，再换成数据库持久化实现，比如 PostgreSQL。

长期记忆

短期记忆出了这场对话就不管用了。

长期记忆是跨会话的那一层：

这次聊出来的用户偏好，下次还能取出来用。

它把数据放在 Store（存储）里，按命名空间和键来组织。

命名空间一般拿用户 ID 这类东西来分，键指向具体那一条。

项目 短期记忆 长期记忆
范围 一场会话内 跨会话
管什么 当前对话的状态和上下文 用户偏好、业务事实这类要长期留着的信息
存在哪 内存或数据库 Store，按命名空间和键组织
解决什么 对话连得上 换一场对话还认得你

让它好用一点

流式处理

用户等结果的时候，屏幕空着和一直在动，体感差很远。

流式处理就是让结果边生成边往外送。

好处有两个：

用户很快就能看到字，等待的焦虑就小；

过程看得见，出问题也能早点发现。

常用的流式输出有三种：

  • updates，每一步的状态变化
  • messages，模型逐字往外蹦的内容
  • custom，你自己往里塞的事件

按需要挑，也可以几种一起用。

结构化输出

模型默认的回复是一段自然语言。

人读没问题，程序读就麻烦了。

同一件事，模型这次多说一句，下次换个措辞，程序只能靠猜。

结构化输出的办法是先给它一个结构定义，让它照着填。

最终拿到的是符合指定结构的数据，字段名、类型都可以提前定义。

程序拿到就能直接用，不用再去猜。

最后一块

中间件

中间件管的是那些跟某一步无关、但很多步都要做的事。

写过 Java 的对这个概念应该不陌生。

Spring 里的 AOP，面向切面编程，也是类似的做法：

不改业务代码，在外围把这些事加上。

LangChain 的中间件思路也相近，只不过它挂在 Agent 的运行过程上。

Agent 跑起来之后，常见的生命周期钩子有这些：

钩子 什么时候执行
before_agent 整个 Agent 开始之前，一次
before_model 每次调模型之前
after_model 每次模型返回之后
after_agent 整个 Agent 结束之后，一次

除了这四个生命周期钩子，还可以用 wrap_model_call 和 wrap_tool_call 把模型调用、工具调用包起来，在调用前后统一处理。

中间件能做的事不少：

  • 按用户身份挂不同的提示词
  • 限制模型能看到哪些工具
  • 约束输出的格式
  • 失败了重试，或者换个模型顶上
  • 到次数了就提前收手
  • 检测敏感信息
  • 记日志，做分析

不用改业务代码，换一套中间件就换一套规矩。

到这里，九个组件就都讲完了。

上手的时候不用一次配齐。

模型和消息是起步的地方，剩下几块，等你真遇到那个问题再回来加。

记不住上一轮，就回来加记忆；

页面上一直空着，就回来加流式；

程序接不住那段文字，就回来加结构化输出。
