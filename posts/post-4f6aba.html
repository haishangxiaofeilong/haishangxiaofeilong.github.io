Redis 集群到底有几种方案？先把主从复制讲透

2026-08-07 4094 字— 次阅读

Redis 集群到底有哪几种玩法？

这是后端面试里出场率极高的一道题。

标准答案就三个：

主从复制、哨兵模式、分片集群。

三者各自解决不同的痛点，而且彼此之间还能牵出一串延伸问题。

比如主从数据到底怎么同步？

怎么让 Redis 又高并发又高可用？

你们线上用的是单点还是集群？

分片集群里数据怎么落、怎么取？

还有最棘手的集群脑裂怎么防？

本文先把主从复制这条线彻底讲透。

一、主从复制解决什么问题

单台 Redis 不是不能扛，是扛不到太高，并发能力有明显的天花板。

想往上抬，最常规的做法是搭一套主从集群，同时把读写拆开。

这时候就不止一台 Redis 了，而是一个主节点领着若干从节点。

主节点叫 master，从节点叫 slave，也可以叫 replica。

二、读写分离怎么提升并发

master 专职接写请求，也就是增删改。

slave 专职接读请求。

Redis 的真实业务基本都是读多写少，让多个 slave 去分摊读，并发上限自然就抬上去了。

举个直观例子：

如果单台 Redis 的读请求成为瓶颈，可以通过增加多个 slave 分担读压力，从而提升整体读吞吐能力。

但实际提升效果还会受到网络、机器配置、热点数据等因素影响。

三、主从同步的第一种模式：全量同步

同步分两种情况：

全量同步和增量同步。

先看全量。

我们拿一主一从举例，左边 master，右边 slave。

第一步，slave 主动向 master 发起同步请求。

接着 master 会根据 slave 携带的 replid 和 offset 判断当前同步状态。

如果 slave 是第一次同步，或者 master 无法根据已有信息进行增量同步，就会触发全量同步。

此时 master 会返回 FULLRESYNC 响应，其中包含新的 replid 和当前复制偏移量 offset，slave 收到后保存这些信息，之后再开始加载 RDB 文件。

接着 master 执行一次 BGSAVE，也就是 fork 一个子进程去生成 RDB 文件。

RDB 生成完就推给 slave，slave 收到 RDB 文件后，会根据全量同步流程替换本地数据集，然后加载 RDB 内容。

但还差最后一脚。

master 在生成 RDB 的这段时间里，要是又接到了新的写请求，刚才那份 RDB 就已经过时了。

怎么办？

master 会把这段期间的新命令先写进一个叫 repl backlog 的日志缓冲区，等 RDB 发完，再把这份增量日志发给 slave 执行。

两边才算真正完全同步。

全量同步的完整过程就是这样。

repl backlog 是 master 维护的环形缓冲区，并不是永久日志。

不过这里藏着两个必须说清的问题。

第一，master 凭什么知道 slave 是不是第一次来同步？

第二，后面再次同步时，基本都从 repl backlog 里取命令，它怎么保证每次不多取也不少取，刚好是 slave 缺的那部分？

要回答这两个问题，得先认识两个概念。

四、replication id：判断是不是第一次同步

第一个概念叫 replication id，简称 replid，它是数据集的身份标记。

如果 master 和 slave 的 replid 相同，说明他俩属于同一个数据集。

想一想，主和从的数据是不是得是同一份？

那当然必须一致。

每个 Redis 主节点都有自己的 replid，它用于标识当前数据集的复制历史。

slave 完成同步后，会保存 master 的 replid，后续再次同步时会携带这个 replid 和 offset。

当 slave 再次发起同步时，会携带之前保存的 replid 和 offset。

master 会根据这两个值判断，是否可以从 repl backlog 中继续增量同步。

如果 replid 不匹配，或者 offset 已经不在 repl backlog 的有效范围内，master 会触发全量同步，并通过 FULLRESYNC 返回新的 replid 和 offset，slave 保存后建立新的复制关系。

master 返回 FULLRESYNC 后，slave 保存新的 replid 和 offset，随后 master 执行 BGSAVE 开始全量数据同步。

现在第一个问题解决了。

再看第二个：

如果 slave 再来同步时，两边 replid 一样，说明之前同步过，master 就不会再生成 RDB，而是直接走 repl backlog。

可问题是，第二次、第三次同步，到底该从这份日志里取多少数据？

这就引出第二个概念：offset。

offset 是一个偏移量，你可以把它理解成一个只增不减的整数计数器。

replication offset 表示复制流中的位置，用于标识主从双方复制进度。

它的用处正在于此：

主从同步版本信息时，会顺带携带 offset。

比如 slave 记录的 offset 是 50，master 的 offset 是 80，那就说明 50 到 80 这段数据还没同步过去。

所以 master 再次同步时，只要把 50 到 80 这段发给 slave 就行。

第二个问题也就解决了。

五、全量同步三步总结

把全量同步串起来，其实就是三步走。

第一，slave 向 master 发起同步请求，master 根据 slave 携带的 replid 和 offset 判断是否可以增量同步。

如果无法继续同步，则进入全量同步流程。

第二，master 执行 BGSAVE 生成 RDB 文件，推给 slave 加载。

第三，master 在生成 RDB 期间接到的新命令，会记进 repl backlog，最后把这份日志发给 slave 执行，流程结束。

六、主从同步的第二种模式：增量同步

增量同步的触发时机，主要是 slave 重启，或者主从数据发生了变动。

流程是这样的：

slave 重启后向 master 发起同步，这次带了两个值，一个是 replid，一个是 offset。

master 先比对 slave 携带的 replid。

如果 replid 一致，并且 offset 仍然存在于 repl backlog 中，就可以继续执行增量同步。

master 会从 repl backlog 里取 offset 之后的数据。

还是那个例子，slave 的 offset 是 50，master 的 offset 是 80，master 就把 50 到 80 这段取出来发给 slave。

增量同步到这就结束了，总共只要两步。

把增量同步也拆开看，就是两步。

第一步，slave 发起请求，master 判断不是第一次，拿到 slave 带过来的 offset。

第二步，master 从 repl backlog 里取 offset 之后的数据，同步给 slave，结束。

到这里，主从数据同步的整套机制就讲完了。

七、回到面试：这道题怎么答

最后回到开头那道面试题。

第一问，介绍一下 Redis 的主从同步。

单节点 Redis 并发有上限，想提并发就得搭主从集群，做读写分离，通常是一主多从：

master 负责写，slave 负责读。

第二问，主从同步数据的流程是什么？这里分全量和增量两种情况。

先说全量同步。

第一，slave 向 master 请求同步，带上 replid 和 offset 两个参数。

master 根据 slave 携带的 replid 和 offset 判断是否可以增量同步。如果无法继续同步，则进入全量同步流程。

第二，master 执行 BGSAVE 生成 RDB 发给 slave 加载。

第三，生成 RDB 期间 master 可能又接到命令，这些命令会记进一个缓冲区，也就是 repl backlog 日志，最后把这份日志发给 slave 执行，主从同步完成。

增量同步更简单。

还是 slave 先请求同步，master 根据 replid 和 offset 判断可以继续增量同步。

第二步，master 从 repl backlog 里取 offset 之后的数据发给 slave，同步完成。
