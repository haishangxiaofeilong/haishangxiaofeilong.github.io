一个登录框，如何让黑客绕过密码？聊聊 SQL 注入

2026-07-16 5084 字— 次阅读

面试官问：

"你做Web项目的时候，后台接口肯定要跟数据库打交道。那你知道什么是SQL注入吗？"

一句话：

SQL注入就是攻击者通过构造恶意的输入参数，拼进你的SQL语句里，让数据库执行他想要的任何操作。

说白了，就是你的SQL语句不再是由后端代码生成的，而是被用户的输入给劫持了。

为什么SQL注入能成功？

核心原因就一个：拼接字符串。

很多新手写查询逻辑时，习惯把用户输入直接拼到SQL字符串里——就像把两块乐高积木随便摁在一起，没做任何校验，攻击者只要往里面塞一段特殊的"积木"，就能让整个结构变形。

举个最经典的例子

假设你有一个登录接口，后端代码是这样的：

// ❌ 错误写法：直接拼接用户输入
String sql = "SELECT * FROM users WHERE username = '" + username + "' AND password = '" + password + "'";
Statement stmt = conn.createStatement();
ResultSet rs = stmt.executeQuery(sql);

正常用户输入用户名 admin、密码 123456，拼出来的SQL是：

SELECT * FROM users WHERE username = 'admin' AND password = '123456'

没问题，对吧？

但如果攻击者在密码框里输入 ' OR '1'='1，拼出来的SQL就变成了：

SELECT * FROM users WHERE username = 'admin' AND password = '' OR '1'='1'

'1'='1'** 永远为真**，所以这条SQL会直接返回所有用户的数据，攻击者不用知道密码就能登录进去。

这就叫SQL注入。

SQL注入能做什么？

不只是登录绕过，注入的威力远比你想的大。

攻击类型 效果 典型注入语句
认证绕过 不用密码直接登录 ' OR '1'='1
数据泄露 查走整张表的数据 '; DROP TABLE users; --
联合查询注入 从其他表偷数据 ' UNION SELECT username, password FROM admins --
盲注 逐字节猜解数据（页面无回显时） ' AND SUBSTRING(password,1,1)='a' --
堆叠注入 一次请求执行多条SQL '; INSERT INTO admins VALUES('hacker','pwd'); --

1. 认证绕过（最基础）

上面已经讲过了，用户输入 ' OR '1'='1 就能直接跳过密码验证。

2. 数据泄露 —— UNION 注入

如果页面会把查询结果展示出来（比如搜索功能），攻击者可以用 UNION 把其他表的数据"偷"过来。

假设有个搜索接口：

// ❌ 拼接用户搜索关键词
String sql = "SELECT * FROM products WHERE name LIKE '%" + keyword + "%'";

攻击者输入：

' UNION SELECT username, password, email, role FROM users --

拼出来的SQL变成了：

SELECT * FROM products WHERE name LIKE '' 
UNION 
SELECT username, password, email, role FROM users --'

数据库会先查 products 表（结果为空），再把 users 表的账号、密码、邮箱全部 union 过来，直接展示在页面上。

3. 盲注（页面无回显时的攻击方式）

有些系统做了防护，注入后页面不报错也不返回数据，这时候攻击者还能用盲注。

原理是：通过构造条件判断，利用页面返回的"有结果/无结果"来逐字猜解数据。

比如攻击者想猜管理员密码的第一位是不是字母 a：

admin' AND SUBSTRING(password, 1, 1) = 'a' --

如果页面返回正常，说明第一位就是 a；如果返回异常或无数据，就不是。

攻击者可以写个脚本自动化这个过程，从第一个字符猜到最后一个字符，虽然慢，但完全能跑出来。

为什么拼接字符串会有这么大的问题？

说人话就是：数据库分不清哪些是代码、哪些是数据。

当你用字符串拼接的方式构造SQL时，数据库拿到的只是一坨纯文本，它不知道哪部分是预先写好的查询逻辑，哪部分是用户传进来的内容。

用户输入的任何单引号、注释符、逻辑运算符，都会被当成SQL语法的一部分来解析。

打个比方：

你让餐厅厨师做一道菜，菜谱上写的是"放适量盐"。

但攻击者往菜谱上偷偷加了句"再倒一桶洗衣粉"。

厨师分不清这是正常的"适量盐"还是恶意的"倒洗衣粉"，照单全做——菜就变质了。

怎么防御SQL注入？

防御的核心思路就一条：让数据库明确区分代码和数据，永远不要信任用户输入。

方案一：预编译语句（Parameterized Query）—— 首选方案

这是最有效、最推荐的防御方式。预编译的原理是：先把SQL模板发给数据库编译好，再把用户数据单独传过去，两者永远不会混在一起。

继续上面的登录例子，改成预编译写法：

// ✅ 正确写法：使用 PreparedStatement
String sql = "SELECT * FROM users WHERE username = ? AND password = ?";
PreparedStatement pstmt = conn.prepareStatement(sql);
pstmt.setString(1, username);   // 第一个问号填用户名
pstmt.setString(2, password);   // 第二个问号填密码
ResultSet rs = pstmt.executeQuery();

注意看，这里 SQL 模板里的 ? 是占位符，用户数据通过 setString() 方法单独传进去。

即使攻击者输入 ' OR '1'='1，这个值也会被当作纯字符串传给数据库，数据库会去查"用户名恰好等于 ' OR '1'='1"的用户，而不会把它当成SQL语法来解析。

本质上是数据库先编译好了SQL的执行计划，用户参数只能作为数据参与查询，不会改变原 SQL 的语义结构。

Java 中的几种预编译用法

  • MyBatis：用 #{} 而不是 ${}
    • #{username} → 预编译参数，安全
    • ${username} → 直接字符串替换，等同于拼接，不安全
<!-- ✅ 安全：预编译 -->
<select id="login" resultType="User">
    SELECT * FROM users WHERE username = #{username} AND password = #{password}
</select>
<!-- ❌ 危险：字符串拼接 -->
<select id="login" resultType="User">
    SELECT * FROM users WHERE username = '${username}' AND password = '${password}'
</select>
  • JPA / Hibernate：用命名参数或位置参数，别用字符串拼接
// ✅ 安全
@Query("SELECT u FROM User u WHERE u.username = :username AND u.password = :password")
User login(@Param("username") String username, @Param("password") String password);

方案二：输入校验与过滤 —— 辅助手段

预编译是最核心的防御，但除此之外还可以加一层输入校验作为纵深防御。

  • 白名单校验：只允许预期的字符通过，比如用户名只允许字母、数字、下划线
  • 长度限制：限制输入字段的长度，防止超长 payload
  • 特殊字符转义：把 '、;、--、/* 等SQL关键字字符转义

但要注意：输入校验不能替代预编译。因为它本质上是在做"内容识别"，而攻击者的手法层出不穷，靠规则去拦截永远有漏网之鱼。

打个比方，预编译是把数据和代码放在两个不同的保险箱里，而输入校验只是在门口安排了一个保安——保安再厉害，也挡不住所有可能的伪装。

方案三：最小权限原则

数据库连接账号不要用 root 或 sa 这种超级管理员账号，而是创建一个只有必要权限的专用账号。

权限 推荐做法
SELECT 业务查询需要，开放
INSERT 业务写入需要，开放
UPDATE 业务修改需要，开放
DELETE 尽量不开，用软删除代替
DROP / ALTER 绝对不开放
EXECUTE 绝对不开放

这样即使真的发生了注入攻击，攻击者也只能做有限的操作，没法删库、没法改表结构、没法执行系统命令。

方案四：WAF（Web应用防火墙）

WAF 会在流量进入应用之前做一次扫描，识别并拦截常见的注入特征，比如 ' OR、UNION SELECT、DROP TABLE 之类的关键字组合。

它的作用更像是第二道防线，不能替代代码层面的防御，但在应对未知漏洞和零日攻击时能提供额外的保护。

总结一下

防御手段 重要性 说明
预编译语句 必须 从根源上杜绝注入，所有参数化查询框架底层都是这个
输入校验 应该 辅助手段，不能单独依赖
最小权限 应该 缩小攻击面，降低实际危害
WAF 可选 额外保护层，不能替代代码修复

说到底，SQL注入不是什么玄乎的东西，它就是字符串拼接 + 用户可控输入带来的必然结果。

只要业务代码坚持参数化查询，不直接拼接用户输入，并结合输入校验、权限控制等措施，就能从根源上大幅降低 SQL 注入风险。
