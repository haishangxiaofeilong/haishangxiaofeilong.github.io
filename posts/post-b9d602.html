MySQL 索引有哪些设计原则？

2026-08-21 3825 字— 次阅读

面试被问“索引怎么设计”，最怕背成几条军规。

索引该怎么建，没有放之四海皆准的答案。

唯一准绳是你的业务：

查询要跑得快，写入也不能被拖垮。

但有一条总纲先摆出来：

索引是用写入和维护成本，换来的查询提速。

记住这一句，下面九条原则都是它的延伸。

下面这些不是 MySQL 的硬性规定，而是索引设计中常见的经验原则。

真正落地时，还是要结合数据量、查询模式和执行计划来判断。

九条原则，先速览一遍

原则 一句话记法
数量克制 索引不是越多越好，控制维护成本
查询优先 优先服务高价值、高频或高成本查询
选择性优先 优先考虑过滤能力强的列
字段短小 索引键越短，通常越节省空间和 IO
NULL 看场景 NULL 可以建索引，关键看数据分布和查询
避开易变 高频更新列要评估额外索引维护成本
联合优先 高频多条件查询优先考虑联合索引
顺序匹配 根据等值、范围、排序和查询模式安排顺序
主键有序 聚簇索引主键尽量递增或趋势递增

下面拆开讲。

索引别堆太多，低频字段也别建

先说反直觉的一点：

索引堆得越多，写入越慢。

一张表的索引数量要克制，5 个左右只是很多业务中的经验参考，不是硬性限制。

你的表有上百个字段、确实每个都要查，超一点也没办法；

小表可以多挂几个，大表更得谨慎，索引数量没法用同一个数字一刀切。

但方向要明确：

别给每一列都挂一个索引。

原因回到总纲。

索引加速的是查询，代价落在增删改上。每多一个索引，写数据时就多维护一棵 B+ 树。

索引还挑使用频率。

索引通常优先服务高频查询，但低频查询也要看实际成本。

对于低频查询，不要因为“偶尔会查”就立即增加索引，需要评估它的执行成本、查询耗时和索引维护成本。

如果一条 SQL 虽然低频，但每次执行都扫描海量数据、严重影响业务，同样可能值得专门优化。

类比一下：

索引像书的目录。

目录越细，查着是快，可每次改内容都得维护所有目录，目录本身还占页数。

书越厚，这账越不划算。

优先考虑“选择性高”的列

建索引要看列的区分度。

严格来说，列中不同值的数量叫基数，而不同值数量占总行数的比例，可以用来衡量这列的选择性。

一般来说，选择性越高，索引通常越容易发挥过滤作用、越容易通过索引快速缩小扫描范围，但最终还是要结合具体查询和执行计划判断。

反过来想就清楚了：

性别只有男、女两个值，给它能筛掉多少数据？

几乎筛不动。

这种低基数列单独建索引通常收益有限，但如果它是联合索引里和高频等值条件配合的一列，价值就得另说。

索引字段，越短越省 IO

这一条常被忽略，但它直接决定树的形状。

B+ 树能快，靠的是树矮。

树一高，查找路径上要访问的节点就多，磁盘 IO 跟着涨。

字段越短，一个索引节点能塞下的键就越多，扇出越大，整棵树越矮。

同样是存一批数据，INT 只占 4 字节，而较长的字符串索引键可能占用几十甚至上百字节，相同树高下能装的记录数差出一大截。

前提是：

业务死规定要用 UUID 这类较长的主键，你也没辙，只能跟着业务走。

但只要能给短字段，就别用长字段。

类比一下：

把 B+ 树的每个节点想成一格固定大小的抽屉，索引键就是往里放的物件。

物件越小，一格能装下的越多，从根节点找到叶子要走的层数就越少；

而每下一层就要读一次磁盘，层数少了，IO 次数自然就降下来。

两类列要算清账：允许 NULL 的看场景、频繁更新的算维护成本

NULL 在数据库里是个特殊存在，但它本身并不意味着不能建索引。

在 MySQL 中，允许 NULL 的列同样可以建立索引，IS NULL、IS NOT NULL 等条件也可能使用索引。

真正要关注的是这列的数据分布和查询选择性。

比如某一列 99% 都是 NULL，查询 WHERE column IS NULL 要返回几乎整张表，索引的过滤能力就很弱，优化器可能直接走全表扫描。

所以重点不是“看到 NULL 就不建”，而是这列能不能有效过滤数据、查询是否真的能从索引里获益。

频繁更新的列也别急着建。

如果一个列频繁更新，而它又参与索引，那么每次更新都可能带来额外的索引维护成本。

对于某些更新场景，还可能涉及索引记录的移动以及页空间调整等额外开销。

类比一下：

索引就像按某个字段排好序的档案柜。

这个字段天天变，等于每份档案隔三差五要换个格子重新归位——数据改一次，索引也得跟着挪一次，额外的维护成本就是这么来的。

多用联合索引，少堆单列索引

如果业务中经常出现多个字段组合查询，可以优先考虑联合索引，而不是机械地给每个查询字段分别建立单列索引。

联合索引的价值，不只是覆盖索引。

它可以更好地服务多条件查询，也有机会减少重复索引，并提高覆盖索引的概率。

联合索引 (a, b, c) 的叶子节点带着 a、b、c 和主键，要查的列如果都在这棵索引里，就不用回表查数据页，查询一步到位。

单列索引分别服务单个字段的过滤条件；

对于多个字段的组合查询，优化器有时可以通过 Index Merge 合并多个单列索引，但通常不如针对查询模式设计合理的联合索引直接。

维度 联合索引 (a,b,c) 多个单列索引
覆盖查询 更容易覆盖多个查询字段 通常覆盖能力较弱
查询能力 可同时服务符合最左匹配的多条件查询 更适合独立字段查询
空间与写入 有机会减少重复索引 索引过多会增加维护成本
顺序约束 有，需要考虑列顺序 单列本身没有顺序依赖

联合索引排顺序，最左匹配是基础规则

联合索引建好了，列的顺序就是命门。

排顺序时，不要只盯着“谁的基数高”，更重要的是结合真实 SQL 来看：

高频查询涉及的字段优先考虑；

等值条件通常放在前面；

范围查询字段通常放在等值条件之后；

再结合字段基数、排序和分组需求调整；

尽量让一套索引服务多条高频 SQL。

原因在最左匹配原则。

联合索引按你定义的列顺序，把数据一层层排好序。

先看最左列，最左列相同再看第二列，依次往下。

它先保证最左列全局有序，后面的列只在“前面列相等”的小范围里才有序。

比如 WHERE a = ? AND b = ? AND c > ?，通常会优先考虑 (a, b, c)，而不是机械地按字段基数从高到低排列。

等值条件 a、b 能连续锁定索引前缀，再利用 c 做范围扫描。

类比一下：

通讯录按“姓 → 名”排。

找“姓张、叫三”的人，翻到张姓那段再找三，很快；

只想找“叫三”的人、不知姓氏，就只能从头翻到尾。

联合索引一模一样——跳过最左列，原本的有序优势就接不上。

主键尽量自增，少一次页分裂

如果表有主键索引，尽量让主键具有递增或大致递增的特性。

自增整数是最常见的选择。

连续递增的主键通常能让新记录更多地追加到索引末尾，减少随机插入带来的页分裂和页空间碎片，写入效率更高。

像 UUID v4 这类随机性强的主键，插入位置更随机，更容易引发页分裂；

而 UUID v7、雪花 ID 等趋势递增的方案，情况就好得多。

顺手记一个实战经验：

在离线的大批量数据导入场景中，有时可以评估是否先移除部分二级索引，导入完成后再统一创建，以减少导入过程中的索引维护成本。

但是否这样做，还要结合数据量、业务可用性和索引重建成本来判断，在线业务或需要保证查询可用的场景不能简单照搬。

九条原则说到底，就是三件事：

建多少、建哪些、怎么排。

建多少——索引数量要克制，优先服务高价值查询，低频字段评估收益后再决定。

建哪些——优先考虑过滤能力强的列，NULL 列结合场景判断，频繁更新列算清维护账，字段越短越好。

怎么排——多用联合索引，根据等值、范围、排序和查询模式安排顺序，主键尽量递增或趋势递增。

把这九条装进这个框架，索引该怎么建，心里就有谱了。

唯一不变的准绳还是开头那句：

用写入和维护，换查询提速；

而所有原则，最终都要回到你的真实查询和数据分布上去校验。
