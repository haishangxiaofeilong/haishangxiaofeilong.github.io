要不要上 TypeScript，先算这两个数

2026-09-13 2227 字— 次阅读

大公司招人，几乎都要求会 TypeScript。

小团队拿到需求，只想赶紧把页面发出去。

本来就是同一门语言衍生出来的东西，两边态度差这么多，吵了很多年也没个结果。

其实 TypeScript 不是新语言。

它是在 JavaScript 基础上加了一套类型系统，写代码的时候就能做静态检查。

要不要用它，跟技术先不先进没关系。

只看两个数：

这个项目打算活多久，平时有多少人碰它的代码。

TypeScript 到底多做了点什么

JavaScript 是动态类型。

变量像个不挑食的盒子，数字塞得进，字符串也塞得进。

JavaScript 本身不会像 TypeScript 那样，对这些类型关系做系统的静态检查，很多问题得等代码运行到那里才暴露。

用户点下按钮的那一刻页面白屏，你才知道哪个地方传错了。

TypeScript 会在开发阶段把这些类型关系检查清楚。

函数收什么参数、返回什么结构，都能用类型写下来。

写错了，编辑器当场标红，很多问题在运行之前就能被发现。

差别就这么一点。

后面的好处和麻烦，都是这一点带出来的。

大公司为什么离不了它

大公司的代码库动辄几十万行，几十个模块互相调用。

想改一个核心字段的名字，JavaScript 也能靠 IDE 帮你找，但复杂项目里，工具理解到什么程度，很依赖代码本身。

真漏掉一处，问题就可能一路带到线上。

TypeScript 里，数据结构和它的使用方之间有明确的类型关系。

你改了源头的数据结构，受影响的地方更容易被找出来。

哪些位置要跟着改，不用全靠猜。

这种重构时的确定性，让团队敢去动老代码。

不然技术债只会越堆越高。

模块越多，调用关系越绕，这种确定性就越值钱。

另一件事是协作。

几十人的团队，谁也看不完别人写的模块。

类型定义摆在那，前端跟后端对接口、新人接手老项目，很多时候不用先翻一遍过期文档。

一个函数要传什么、返回什么，看一眼就知道。

原来是口头约定，现在写进代码里，机器盯着。

小团队为什么嫌它烦

麻烦先出在前期成本上。

小项目功能单一，讲究快速上线。

JavaScript 拿到数据随手就用，结构变了随时改。

换成 TypeScript，你得先把类型定义好。

数据结构一复杂，为了把类型关系描述清楚，还得写一堆绕来绕去的类型定义和泛型。

圈内把这种活叫类型体操。

核心业务逻辑可能就几十行，为类型花的力气反而更多。

这就让人觉得本末倒置了。

另一处麻烦在工程配置上。

浏览器不能直接执行 TypeScript 的类型语法，前端项目通常得先把它转换成 JavaScript 才能跑。

所以项目工程里要处理类型检查，以及 TypeScript 到 JavaScript 的构建流程。

有些第三方库没有完整的类型声明，还得额外补类型，不然编辑器照样可能报错。

一个一两周就要交付的活动页，或者一个个人博客，为这个配一遍，确实太重。

配置花的时间，反而比写业务代码还多。

分界线不在公司大小

上面这些，都是表象。

真正决定要不要用的，是项目的生命周期和协作人数。

一个小项目预期要长期迭代，将来可能变成正式产品，早期多花点约束成本是划算的。

反过来，大公司内部做一个只活三天的抽奖页，直接上 JavaScript 才合理。

维度 JavaScript TypeScript
类型检查 主要依赖运行时和其他工具 开发阶段就能做静态检查
改数据结构 依赖 IDE 推断和人工检查 类型关系明确，更容易定位受影响的位置
团队协作 靠文档和口头约定 类型定义能补上一部分文档
前期成本 低，随手就能写 要先定义类型，复杂结构还得写类型定义和泛型
工程配置 通常更简单 要处理类型检查和构建流程
适合的场景 短期、功能单一、少人维护 长期迭代、多人协作

另外，现在主流前端框架和工程工具基本都支持新旧代码逐步共存。

你可以先给核心模块补上类型，其余部分先放着。

不必一上来就追求 100% 覆盖。

TypeScript 更像一笔投资，拿前期写代码时多花的约束成本，换后期维护和协作时的省心。

项目活得短、碰它的人少，这笔钱花出去收不回来。

项目活得长、碰它的人多，这笔账就是划算的。

要不要上，先算这两个数：

项目准备活多久，平时有多少人碰它的代码。
