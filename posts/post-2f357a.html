大模型推理到了推理引擎这一步，到底要管哪些事

2026-09-10 2469 字— 次阅读

我在上篇《Decode 每轮都重算一遍历史 token 吗：聊聊 KV cache》里讲过——KV cache 让 Decode 每轮不用重算历史的 K 和 V，推理才快得起来。

可这些阶段到底是谁在背后把它们跑起来的？

这一篇把镜头从"原理"拉到"工程"，聊聊推理引擎本身。

你写代码调模型，通常就是发一段提示词过去，过一会儿一串 token 就回来了。

模型权重本身只描述网络参数，并不负责请求怎么排队、Prefill 和 Decode 怎么调度、KV cache 在显存里怎么分配。

这些"把提示词送进模型、算注意力、跑 Decode、把 K 和 V 写进缓存"的运行时工作，都是由背后的推理引擎来负责。

业界不用自己造轮子。

vLLM、SGLang、TensorRT-LLM 都是常见的高性能推理框架；

Ollama 则更偏向本地模型运行和轻量服务，两者解决的问题有重叠，但定位并不完全一样。

不管哪一款，要解决的核心问题都一样：

让 Prefill 和 Decode 在显卡上真正跑起来，还得把 KV cache 的空间管好。

Prefill 处理输入、Decode 逐 token 反复生成，这个区别我在《大模型推理的两阶段：一次 Prefill，加上多次 Decode》里讲过；

一次完整推理要过的几道工序，在《一次完整推理，模型背后要走完 5 道工序》里也拆过。

Prefill 和 Decode，为什么要分开实现

回到我们讲过的 Prefill 和 Decode。

单看计算特性，它们就完全是两码事。

Prefill 是把已有的输入 token 批量送进模型，算的是一大坨矩阵运算，通常更偏计算密集型——这时候显卡的计算单元能被充分利用。

Decode 不一样。

它每轮只处理一个新 token，单轮计算量相对小，但还得从显存里读取历史 K 和 V。

尤其在单请求或小批量场景下，这种"每次只算一点、却要反复读显存"的活，通常更容易受到显存访问效率的影响。

打个比方。

Prefill 像你一次性搬一大箱货上楼，累是累在分量重；

Decode 像你每过几分钟就跑下楼取一个小件，真正花时间的是上下楼的路——也就是频繁访问显存的成本。

既然 Prefill 更偏计算密集、Decode 更受显存访问效率影响，引擎如果把两者用同一套方式调度，两边都发挥不出优势。

所以实际实现里，Prefill 和 Decode 往往会采用不同的调度策略和计算路径：

Prefill 更适合利用大规模矩阵计算，Decode 则需要围绕逐 token 生成和 KV cache 读取来做优化。

推理引擎负责根据当前请求状态，把显卡的计算资源调度给合适的任务。

企业级部署，为什么特别看重并行和批处理

光把Prefill 和 Decode 跑起来还不够。

把个人使用和企业部署拉开距离的，是同一时刻有多少请求。

你一个人用 Ollama，同一时刻基本就你一个问题；

企业把模型部署出去，往往是几十上百个客户端同时发问。

这就有个绕不开的问题：

批处理。

为什么批处理这么关键？

关键还得从 Decode 的工作方式说起。

Decode 每轮只算一个 token，单个请求带来的计算量比较小，很难像 Prefill 那样充分利用 GPU 的计算资源。

把多个请求的 Decode 放进同一批里，每个请求各出一个 token，GPU 一次就能处理一批 token。

这样可以提高资源利用率，进而提高单位时间能够生成的 token 总量。

注意，批处理主要提升的是整体吞吐，不是让某一个请求的单次 Decode 变快。

而且，大模型推理里的批处理并不是简单地"等一批请求凑齐再一起算"。

因为不同请求的输入长度、生成长度都不一样，有的请求已经生成完了，有的还在继续生成。

现代推理引擎通常会采用 Continuous Batching（连续批处理）：

请求可以动态加入和退出当前批次，显卡则持续处理当前活跃的请求。

这也是企业级推理引擎和简单本地推理程序拉开差距的地方之一——它不仅要会算，还得持续调度一大批生命周期不同的请求。

这也就是企业级推理引擎都在批处理上死磕的原因——吞吐上不去，同样一张卡能服务的用户就少，成本就高。

批处理之下，KV cache 怎么管

前面讲过，KV cache 的空间分配、写入和读取，主要由推理引擎负责。

到了批处理场景，这件事变得更讲究：

同一时刻有那么多请求，每个请求都有自己的 KV cache，长度还不一样。

引擎不仅要记录每个请求用了多少 KV cache，还要在 Decode 时准确找到它对应的 K、V。

这就引出下一个问题：

一种比较直接的做法，是给每个请求按照可能的最大序列长度预留一块连续的显存空间。

问题是，请求实际生成的长度往往远小于这个上限，这块预留空间可能长期用不满。
