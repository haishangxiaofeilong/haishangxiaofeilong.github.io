MySQL 联合索引：最左列为什么不能跳过

2026-08-19 4150 字— 次阅读

面试官问联合索引，十有八九会顺着问最左匹配。

这玩意儿看着不起眼，却是索引有没有命中、命中几列的分水岭。

一句话结论

联合索引对列的命中是有顺序的，守一条硬规矩：

查询条件必须从最左列开始匹配，中间不能断。

最左列一旦没出现在 WHERE 里，后面那些列写得再全，在常规最左前缀匹配下，这个索引通常也帮不上忙。

最左匹配原则到底在说啥

说白了，联合索引就是按你建索引时写的列顺序，把数据一层一层排好序。

这种排序方式，决定了查询时必须从最左列开始才能利用有序性——这就是"最左匹配原则"的由来。

比如给一张 user 表建了 (age, gender, city) 这个联合索引，B+ 树里的顺序是：

先按 age 排，age 相同的再按 gender 排，gender 还相同才按 city 排。

查询的时候也得顺着这个顺序来。查询条件能够从索引的最左列开始，按照索引列顺序连续使用 age → gender → city，就满足最左前缀匹配。

为什么非得从最左开始

想象一本按"姓氏 → 名字"排的通讯录。

你想找"姓张、叫三"的人，翻到张姓那一段再找三，很快。

但你只想找"名字叫三"的人，姓氏不知道，那就没法利用这份有序性做快速定位了。

通讯录整体是按姓氏排的，光凭名字你只能从头翻到尾。

联合索引一模一样。

它先按最左列全局有序，后面的列只在"前面列相等"的小范围里才有序。

所以跳过最左列去查后面的列，联合索引原本的有序优势就很难直接利用起来。

通常情况下，无法按照最左前缀进行高效定位。

字段顺序固定，WHERE 条件的顺序随便

这是最容易被绕晕的一点。

联合索引的顺序是 (age, gender, city)，可下面这条 SQL 照样能命中索引：

select * from user
where city = '北京' and age = 10 and gender = 'male';

原因是对于 AND 条件，优化器会根据查询条件和索引情况进行等价的访问路径优化，并不要求你在 SQL 中按照索引定义的顺序书写条件。

AND 之间换顺序，结果不变，优化器照样能利用 (age, gender, city) 这个索引。

要分清两件事：

索引定义里写死的列顺序不能乱。

WHERE 里条件先后只是写法，优化器兜住了。

哪些写法能命中，哪些只能命中一部分

还是这张 (age, gender, city) 的表，把常见写法列一下：

WHERE 条件 常规最左前缀匹配 说明
age=10 and gender='male' and city='北京' age, gender, city 全程对齐最左前缀
city='北京' and age=10 and gender='male' age, gender, city 条件顺序不影响，优化器照样命中
age=10 and gender='male' age, gender 最左两列，city 没写也行
age=10 age 只用最左列，索引照样生效
gender='male' and city='北京' 无法按最左前缀连续匹配 跳过 age，通常无法像 age → gender → city 一样快速定位。这里说的是传统的最左前缀匹配，现代 MySQL 在特定条件下还存在索引跳跃扫描（Index Skip Scan）等优化，因此"最左列没写 = 索引绝对不能用"并不是绝对结论。

关键点：

断在"后面"只是少用好几列，索引还能用；

断在"最左"，通常就难以按最左前缀高效利用了。

范围查询出现后，后面的列通常无法继续缩小查找范围

等值查询（=）之后还能继续往下匹配。

范围查询（>、<、between）的情况不同，但先说一句：

in 属于多值条件，优化器在不少场景会把它当成多个等值范围来访问索引，不能和 >、< 简单画等号。

下面用明确的区间范围来说明。

看这条：

select * from user
where age = 10 and gender > 'male' and city = '北京';

age 是等值条件，能定位到一段，可以继续向右匹配。

gender 是范围，这一段里 gender 不再全局有序，city 通常就没法接着按等值的方式精确连续定位。

所以这条语句主要靠 age + gender 两列定位，city 一般得不到范围收窄的好处。

更极端一点：

select * from user
where age > 10;

age 本身是范围，排好序的基准列一断，后面 gender、city 通常都没法再基于有序性继续缩小查找范围。

这条语句主要用 age 一列来定位。

可以先记住一个常用规律：

联合索引遇到范围条件后，后面的列通常无法再继续用于缩小索引的查找范围。

不过"无法继续缩小查找范围"不代表后面的列完全没用，某些场景下它们仍可能参与索引条件下推、覆盖索引、排序等优化。

设计联合索引时，通常重点考虑这三个因素

知道了匹配规则，建索引时就得把列摆对位置：

原则 怎么摆 原因
等值查询优先 等值字段放最左 等值能连续锁定前缀，范围会收窄后续可用列
范围查询靠右 范围字段放最右 范围之后列通常难以继续收窄，早放早断
结合查询模式考虑选择性 在查询模式相近、且不影响范围和排序等需求时，再考虑选择性 选择性越好，越能提前把数据筛薄

基数高，说人话就是这一列不重复的值多，也就是选择性好。

比如 user 表 100 行里 age 有 80 个不同值，比 gender 只有男、女两个值区分度高得多。

不过列顺序不能只盯着基数。

联合索引字段顺序首先看实际查询条件、等值还是范围、排序分组需求、选择性，以及是否需要覆盖索引。

在多个字段查询模式相近、又不影响排序和范围查询的前提下，通常优先让选择性更好的字段参与更靠前的索引定位。

一个会打破最左原则的特例

前面说的都是铁律，但有一种情况最左列没写，索引居然还能用。

建一张表：

create table abc (
  id int primary key,
  a int, b int, c int
);
alter table abc add index idx_abc (a, b, c);

然后查：

select * from abc where b = 1 and c = 1;

按最左原则，这该失效才对。

但它没失效。

原因是索引覆盖。

这张表的列就 id、a、b、c 四个，而联合索引 idx_abc 的叶子节点记录了 (a, b, c) 再加上主键 id。

虽然 WHERE 条件只写了 b 和 c，但 select * 需要返回的 id、a、b、c 全部都包含在这个二级索引记录中，因此可以形成覆盖索引，不需要回表。

MySQL 发现这个二级索引能够覆盖查询所需要的全部列，不需要回表。

如果扫描整棵二级索引的成本低于全表扫描，优化器就可能选择扫描这个索引。

再对比一张表：

create table abc2 (
  id int primary key,
  a int, b int, c int, d int
);
alter table abc2 add index idx_abc (a, b, c);

同样的查询放到 abc2 上，情况就不一样了。

因为 select * 还需要获取索引中不存在的 d，如果扫描这棵联合索引，就需要额外回表去拿 d。

这时候优化器会重新计算成本：

如果“扫描联合索引 + 大量回表”的成本高于全表扫描，就可能直接选择全表扫描，而不是一定走联合索引。

这个特例看着像是推翻了最左原则，其实并没有。

这里利用的是覆盖索引扫描：

即使无法按照 (a,b,c) 的最左前缀高效定位，索引本身仍然包含查询所需的全部列，优化器可能选择扫描整棵二级索引，从而避免回表。

小结

WHERE 条件顺序要和索引顺序一致吗？

不用，优化器会根据查询条件和索引做等价的访问路径优化，不要求你按索引定义的顺序写条件。

范围查询之后为什么通常难以继续定位？

范围破坏了后续列的有序性，无法再按等值方式精确连续定位，但它们仍可能参与过滤、排序或覆盖索引等优化。

还有一层容易漏掉的：

当查询所需的列全部包含在某个索引里时，即使缺少最左列，也可能因为覆盖索引而选择扫描这个索引。

理解到这一层，最左匹配原则就算真正吃透了。
