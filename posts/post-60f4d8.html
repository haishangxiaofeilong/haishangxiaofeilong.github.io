gRPC 为什么比 HTTP+JSON 快：快不是某一个技术，是4件事叠出来的

2026-09-03 3903 字— 次阅读

内部调用的钱花在哪了

服务之间一次普通的 HTTP+JSON 调用，真正有用的数据占了多少？

一个 user 对象，id、name、email 这几个字段名每条消息都得原样抄一遍。

接口还靠文档约定。

你写 userId，对方写 user_id，两边对不上，这种错编译期查不出来，只能等联调报错了才反应过来。

这些活不产出任何业务价值，纯粹是通信要交的税。

先把对比基准说清楚：

这里默认比的是最常见的 HTTP/1.1 + JSON。

顺带说一句，如果换成 HTTP/2 + JSON 来比，多路复用两边就持平，差距主要剩编码和框架开销，但现实里多数 REST 接口还跑在 1.1 上。

在这个基准下，gRPC 的优势来自几件事叠加：

契约先行、Protobuf 的紧凑编码、强类型代码生成，再加 HTTP/2 扛并发。

HTTP/2 才是底盘

gRPC 快，很大一块要归功于它底层选了 HTTP/2。

HTTP/1.1 一条连接上的并发能力很有限，规范里虽写过管线化，但兼容性问题让它没被广泛采用。

同一条连接上响应得按请求顺序返回，前面慢下来后面照样被拖住。

想提高并发，客户端往往只能多开几条 TCP 连接，连接一多开销也跟着上去了。

这背后的根因，正是 HTTP/1.1 典型的应用层队头阻塞。

HTTP/2 把数据切成二进制帧，每个帧都带着所属流的编号。

多个请求可以同时跑在同一条 TCP 连接上，帧交错着传，接收方按流编号再拼回去。

一个流上的请求和响应，不必等其他流跑完才能进行，这就是多路复用。

有个边界得说清楚：

HTTP/2 消除的是应用层队头阻塞，它底下仍跑在 TCP 上，丢包时其他流可能也跟着等。

头部用 HPACK 压缩省掉重复头信息；

长连接 HTTP/1.1 也有，真正的差别是一条连接就能撑起并发，不用为了并发开一堆连接。

二进制传输：省掉的就是赚到的

编码时，Protobuf 不把字段名写进消息体，而是通过字段编号和类型信息来编码字段和值。

字段越多、字段名越长，JSON 花在重复字段名上的开销就越大，Protobuf 的体积优势也越明显。

序列化要干的活更少，CPU 开销通常比解析 JSON 低。

打个比方。

JSON 像每次发货都把"收件人姓名、详细地址、联系电话"整段抄在箱子上，每条消息都得重抄一遍，箱子一大半都是这些字段名。

Protobuf 只写"1 号的值、2 号的值"，收方手里有一张对照表，按编号认领就行。

stub：把远程调用伪装成本地函数

RPC 是远程过程调用。

你写 getUser(1)，函数在同一个进程里，调完立刻返回。

现在它搬到了另一台机器，拼 URL、发请求、等响应、解析结果全得你自己来。

RPC 想做的就是把这堆网络细节藏起来。

藏的办法是在中间加一层代理对象，叫 stub，也叫桩。

你调 stub，它把参数打包发出去、等回复、再把结果拆包还给你。

服务端有一份对应的骨架，收到请求后去调你真正的实现。

说白了 stub 就是专职跑腿。

你说"去把 1 号用户的资料拿回来"，出门、找人、交接，全是它的事。

契约先行：先写 proto，再写代码

用 gRPC，写业务代码之前得先写一个 .proto 文件。

它是接口描述语言，定义两件事：

数据长什么样，有哪些方法能被远程调用。

message UserRequest {
  int32 id = 1;
}

message User {
  int32 id = 1;      // 等号后面是字段编号，不是默认值
  string name = 2;
}

service UserService {
  rpc GetUser (UserRequest) returns (User) {}
}

在二进制编码里，字段编号才是识别字段的关键，字段名默认不进消息体。

所以改字段名一般不影响兼容性，但编号用过就不该再动，删字段也别把编号分给别的字段。

老客户端还拿着旧对照表，同一个编号它仍按旧字段解读，数据就被解析到错误的字段上。

proto 写好后用 protoc 生成代码，它自带一部分语言能力、其余靠插件扩展；

客户端 stub 和服务端接口由 gRPC 插件补上。

两边类型彻底对齐，字段拼错在编译期就报错，不会拖到上线才发现。

一次调用从头到尾

概念齐了，把一次调用摊开走一遍。

客户端先建一个 channel，它代表到目标服务的一条通信通道。

底下可能有 0 条或多条 HTTP/2 连接，具体由实现决定。

channel 建一次反复用，别每次调用都新建。

有了 channel 就能建 stub，像调本地方法一样发起调用。

stub 把请求序列化成二进制，包装成 HTTP/2 数据帧发出去；

服务端反序列化成对象，路由到你实现的方法，跑完再原路封帧回传。

四种模式，不止一问一答

很多人以为 gRPC 就是发个请求、收个响应。

其实它有四种模式，流式通信在 gRPC 里是一等能力，可以直接写进接口定义。

HTTP 也能做流式，SSE、WebSocket 都行。

区别在于 gRPC 把三种流统一进了 RPC 模型。

一元调用是一个请求对一个响应，跟普通函数一样；

服务端流是客户端发一次、服务端连续返回很多条；

客户端流是客户端连续发很多条、服务端最后给一个汇总；

双向流是两边都能随时发，聊天、实时推送就是它。

打个比方。

服务端流像点一份套餐，厨房一道道菜连续往上端；

双向流像两个人开对讲机，随时说、随时回，谁也不用等谁说完。

业务参数之外：metadata、deadline 和状态码

除了业务参数，一次调用还要带点附加信息。

metadata 是一组键值对，作用类似 HTTP 的头，认证 token、链路追踪的 trace_id 通常放这里，不混进业务参数。

再就是 deadline，表示这次调用允许存活到什么时候。

语义上它是个截止时间点，但你写代码时交的通常是超时时长，框架自己换算。

好处是它能一路往下游传，整条调用链共用同一个终点。

到点没跑完，这次调用就失败并被取消。

要注意取消不等于回滚，已经写进去的数据还在那，收尾得自己处理。

错误处理上，gRPC 用自己的状态码表达 RPC 的最终结果，跟 HTTP 状态码不是一回事。

常见的 NOT_FOUND、PERMISSION_DENIED、DEADLINE_EXCEEDED、UNAVAILABLE 里，最后这个要看情况再重试：

请求幂等、失败又是暂时性的才适合，否则非幂等的写操作可能落进去两份。

拦截器：通用逻辑别写进每个方法

认证、日志、监控这些事，不该在每个业务方法里都写一遍。

gRPC 给的答案是拦截器，相当于中间件。

它包在真正的调用外面：

请求进来先过一道，响应出去再过一道。

客户端和服务端都能装。

典型用法是服务端拦截器统一校验 token，不合法直接拒绝；

再加一个打访问日志，记录方法名、耗时、状态码。

链路追踪也是这么做的，从 metadata 里取出 trace_id 继续往下传。

什么时候不该用 gRPC

但 gRPC 也不是万能的，有几个场景得先想清楚。

一个是浏览器。

前端 JS 碰不到底层 HTTP/2 帧，发不了原生 gRPC，得靠 gRPC-Web：前端用它，中间放一个代理做协议转换。

另一个是对外开放的 API。

第三方更习惯 REST 和 JSON，让人家先装 protoc、再生成代码，接入成本太高。

调试也不方便，二进制在抓包工具里是一团乱码，好在有 gRPCurl，服务端开了反射就能像 curl 一样直接调。

回头看，gRPC 的快不是某一个技术点变出来的。

HTTP/2 让并发通信更高效，Protobuf 把数据编码得更紧凑，代码生成把重复劳动标准化，几件事叠在一起，才形成了它在内部调用中的优势。

所以很多团队的组合是：

内部用 gRPC，对外和浏览器场景按接入成本来选，前端确实想直接调也可以走 gRPC-Web。
