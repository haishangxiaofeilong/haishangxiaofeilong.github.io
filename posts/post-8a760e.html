redo log 和 binlog 的两阶段提交：崩溃了到底谁说了算？

2026-08-31 3633 字— 次阅读

MySQL 里有两个日志经常被放在一起说：redo log 和 binlog。

它们一个管崩溃恢复，一个管主从复制，平时各记各的，偏偏一个事务提交时又得同时落盘。

两阶段提交就是来解决"两条日志怎么对齐"这个问题的，而且它跟分布式系统里那套 2PC 只是设计思想上接近，实现上是两码事。

这里说的两阶段提交，不是分布式事务里协调多个独立参与者的通用 2PC 协议。

MySQL 这里解决的是同一个事务在 InnoDB redo log 和 Server 层 binlog 之间的一致性问题，两者只是都采用了"prepare → 最终提交"的两阶段思想。

两条日志，根本不在一层

redo log 是 InnoDB 存储引擎自己的日志，通常被称为物理日志，记录的是对数据页进行修改所需的重做信息。

它的本职是崩溃恢复：

MySQL 崩了重启，可以靠 redo log 把已经提交、但数据页还没来得及刷回数据文件的修改重新恢复出来，从而保证事务的持久性。

binlog 站在 MySQL Server 层，不属于某个具体存储引擎，是逻辑日志，记录的是事务产生的逻辑变更信息。

它有三种格式：

STATEMENT 直接记录 SQL；

ROW 记录数据行发生了什么变化；

MIXED 是前两者的混合。

生产环境中通常更常见的是 ROW 格式。

binlog 的核心用途是主从复制和时间点恢复。搭一主一从，两台机器的数据同步就靠 binlog 传；

库被误删了，也可以结合全量备份和 binlog，把数据恢复到误操作之前的某个时间点。

redo log binlog
所属层次 InnoDB 引擎层 MySQL Server 层
日志类型 物理日志（记录数据页重做信息） 逻辑日志（记录逻辑变更）
写入/存储特点 循环写入、空间可复用 STATEMENT / ROW / MIXED
主要用途 崩溃恢复、保证持久性 主从复制、时间点恢复

矛盾就藏在"不在一层"里：

一个事务提交，两份日志都要写，那谁先写？

先写谁，都会翻车

设想一主一从两台 MySQL。

从库的数据变更是通过重放主库 binlog 得来的，所以复制链路的事务顺序和内容以 binlog 为准。

现在来个事务，给某个账户余额加一。

要是先写 redo log、再写 binlog，刚把 redo log 写完，binlog 还没动笔，MySQL 崩了。

重启后主库照着 redo log 把余额加了一；

从库从来没收到这条 binlog，余额原样。

主从之间，差了这一块钱。

反过来先写 binlog、再写 redo log，写完 binlog 崩了。

从库已经收到并重放这条 binlog，余额加了；

主库按 redo log 恢复时，里面根本没有这条记录，余额没动。

这回是主库少、从库多。

写入顺序 崩溃位置 主库 从库 后果
先 redo，后 binlog 写完 redo 后崩 有 +1 无 +1 主从不一致
先 binlog，后 redo 写完 binlog 后崩 无 +1 有 +1 主从不一致

如果没有额外的协调机制，只要一个写成了、另一个没写成，就可能导致主从不一致。

两阶段提交给日志加了套状态，把这种撕裂堵上。

两阶段提交怎么走

把它的过程想成发货：

先在自家台账上写一笔"待发"（prepare），再去打印物流单（binlog），物流单打成功了，回头把台账那笔改成"已发"（commit）。

物流单没打成，那笔"待发"就作废，当没发生过。

先把前提说清楚：

本文讨论的是事务型 InnoDB 表，默认采用 innodb_flush_log_at_trx_commit=1、sync_binlog=1 这类强调持久性和复制一致性的配置。

落到 MySQL 上，一个事务的提交流程是这样：

  1. 事务执行 SQL 时，会不断产生 redo log，通常先写入 redo log buffer。到了事务提交阶段，再根据 innodb_flush_log_at_trx_commit 等配置决定相应的写入和刷盘策略。
  2. 收到 commit 指令，在标准的持久性配置下，InnoDB 将包含 prepare 信息的 redo log 刷盘，并把事务状态停在 prepare。
  3. Server 层把这条事务的 binlog 写入并根据 sync_binlog 的配置决定何时同步到磁盘。
  4. binlog 同步成功后，Server 层通知 InnoDB，InnoDB 再写入事务的 commit 状态，完成提交。
  5. InnoDB 释放事务占用的资源，给客户端返回事务成功。

注意第 2 步：

redo log 先落盘，但状态故意停在 prepare。

这一步是给后面占个位："记下了，但还没拍板"。

等 binlog 成功同步到磁盘，再把 redo log 对应的事务写成 commit。

即使 MySQL 在 prepare 和 commit 之间崩溃，重启后也可以根据 binlog 是否存在对应事务继续裁决：

该提交的补提交，该回滚的回滚，最终不会留下 redo 和 binlog 长期不一致的状态。

崩溃了，怎么判断该提交还是回滚

MySQL 重启会触发崩溃恢复。

对于停在 prepare 状态的事务，恢复过程会拿着 redo log 里 prepare 事务的 XID，去 binlog 中查找是否存在对应完整事务，从而决定是补提交还是回滚。

redo log 状态 binlog 情况 恢复动作
未发现该事务的 prepare 记录 — 不恢复该事务
prepare 找不到完整事务 回滚
prepare 找到对应完整事务（XID 匹配） 提交

三种情况拆开看：

如果 redo log 中没有这笔事务对应的 prepare 状态，那么它不属于需要通过两阶段提交恢复机制继续裁决的 prepared transaction。

redo log 停在 prepare，但去 binlog 里找，找不到这条事务的完整记录。说明这个事务没有成功进入 binlog，因此 prepare 状态不能作为最终提交依据，恢复时会将这个事务回滚。

redo log 是 prepare，binlog 里能找到这条事务（靠事务 ID，也就是 XID 对上号），说明 binlog 已经落盘，只是 redo log 还没来得及为这个 prepare 事务补写一条 commit 记录。这种 InnoDB 会自动把它补成 commit，把数据恢复出来。

两阶段提交的本质，是让 redo log 和 binlog 在提交过程中形成一个可恢复的协调状态。

redo log 先进入 prepare，binlog 成功持久化后，再完成最终提交。

这样即使 MySQL 恰好在两个步骤之间崩溃，重启后也能根据 redo log 和 binlog 中的事务状态重新裁决：

binlog 已经持久化，就补提交；

binlog 没有成功写入，就回滚。

正向讲，可能不容易理解为什么非要这么设计；

反过来想就清楚了：

如果只规定两份日志谁先写，那么任意一方写完、另一方还没写完时一旦崩溃，都可能留下"一份有、一份没有"的状态。

prepare 的意义，就是把这个危险的中间状态变成一个可恢复、可裁决的状态。
